# ADR-0005 — Private synthetic Medusa remote staging gate

2026-10-17 (Asia/Dhaka). **PROPOSED; remote approval NOT GRANTED.**

The checkout began clean on `codex/medusa-cloud-run` at `40eea2ed65ba45b023a526ac8b0fa12e4b164056`. Fetched main is merged PR #5, `1b99e23d7e47a82284ea5926e7b9ac0885092e46`; this preparation branch starts there. The founder explicitly authorizes this implementation/PR, superseding historical preparation prohibitions only within this task. ADR-0004 architecture remains in force: Medusa 2.21.2, shared mode, no Redis or worker, IAM-protected service, synthetic data, all operational gates OFF.

Replace the unconditional supervisor rejection with a bundled, review-controlled remote policy. It ships `approved:false`, no approver and no reviewed source SHA. No environment switch or external file can approve it. Local isolated execution still works; unmarked `M2_ENV=staging`, Cloud Run Jobs/executions, Vercel, migrations in the remote service, wrong service/configuration, public configuration, Redis and TLS bypass fail closed. After independent policy activation, fixed metadata reads verify the actual project, region and service account before spawning Medusa. Metadata reads are bounded and never request a token. The ordinary Cloud Run production Node environment is permitted only inside this narrowly approved staging context; `M2_ENV=production` remains rejected.

The expiry is checked at process admission, not continuously. Operators must revoke invocation/stop service at expiry, including already running revisions. The gate does not claim that environment markers or metadata prove IAM, deployed image or secret versions. Those require the independent offline release check and fresh control-plane evidence, followed by actual unauthenticated-denial tests. Runtime SA receives no Cloud Run viewer/IAM inspection privilege just to perform these checks.

`scripts/medusa-staging-release.mjs` validates a resolved service against the canonical template, exact image registry/digest, numeric secret versions, target identity/region/resources and reviewed source marker. Extra container/spec changes, migration settings and secret substitutions reject. It rejects public principals in every supplied service/ancestor IAM policy, including custom-role bindings. It cannot prove that operator-supplied evidence is complete, fresh or authentic; the independent reviewer must verify ancestor coverage, effective `run.routes.invoke` permissions and immutable release artifacts. No deployment command is embedded in CI or the validator.

Approval is two-stage to avoid a self-referential image hash: first seal the reviewed implementation commit and separately approve its policy activation (only the bundled policy changes); then build/scan the resulting image and approve a release manifest binding its exact registry digest, configuration hash, source/activation commits, numeric secrets and IAM evidence. Neither approval is supplied by this PR. A runtime policy never contains its enclosing image digest. Both old exception policies/evaluators remain unchanged and reject this new source scope. A separate reviewed security decision must restore CI; do not update fingerprints merely to obtain green checks.

No new HTTP endpoint, business event, custom DB migration, customer auth, payment, AI, export or print permission. Native startup, shutdown, health/readiness and all existing access denials remain. TLS verification remains `rejectUnauthorized:true` after SSL URL option validation/removal, with a new rejection for the global Node TLS bypass. Native migrations run outside Cloud Run using a separately approved trusted operator environment; the service gate intentionally rejects remote migrations. See [Neon procedure](M2-Neon-Migration-Procedure.md), [operator checklist](M2-Private-Staging-Operator-Checklist.md), and [risk proposal](M2-Remote-Staging-Risk-Proposal.md).

The required acceptance-matrix update adds only a BLOCKED staging note. Its single entry in `M0-protected-files.json` records the new exact bytes plus the previous baseline hash and change rationale; no other protected entry changes, and no security-policy fingerprint is altered.

Rollback: revert preparation code locally; future remote rollback uses an independently reviewed compatible prior image/config/secret version set. PR #5 images cannot run remotely and are not a valid remote fallback. On first activation failure, revoke the approved invoker access and stop/delete only this staging service after recording evidence; retain the database. Native down migrations/restores are never automatic. Shared in-memory state remains unsuitable for live commerce or durable jobs.
