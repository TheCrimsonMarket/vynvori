# ADR 0013 — private Medusa provisioning transport

2026-10-19. Local implementation/test evidence only. Live enrollment, grants, credentials and deployment remain separately gated.

## Decision

Connect the web mapping coordinator to a fixed server-only Medusa SDK client. The already installed/locked SDK 2.21.2 is now a declared direct production dependency of the commerce workspace; no external version, tarball or dependency installation changed. The client exposes provisioning only, not a generic SDK, URL, Admin operation or caller header interface. It uses no JWT storage/cookie jar, no-op logging, no-store, redirect rejection and a bounded timeout. SDK source and loopback tests confirm one fetch with no automatic retry. Successful responses are bounded and checked against the exact project, operation and derived identity key.

Requests carry the central bearer in Authorization, the private service identity in X-Serverless-Authorization, and a separate HMAC proof in X-Vynvori-Bridge. Proof binds the canonical flat body, method/path, target origin/project and central-token hash, expires after a thirty-second clock window and supports key IDs for rotation. Its implementation is byte-identical between the BFF canonical core and the standalone backend, enforced before build. Proof keys are distinct from Portal signing keys, the OAuth client secret and the application encryption keyring. No key or token is sent to browser code.

Cloud Run must validate service identity signature/audience/IAM before the request enters Medusa. The local application additionally rejects browser Origin/Cookie requests, missing/invalid proof and caller-supplied identity fields. TLS verification overrides are rejected by enabled identity/backend settings. The source requires explicit private staging enrollment; its local test mode accepts loopback only. The enrolled backend retains native Admin emailpass policy, enables only the TCM customer provider and keeps all ordinary customer auth routes and Store writes closed. The single current exception is POST /auth/customer/tcm/provision, only when the trusted bridge service was registered by its loader.

## Native idempotency

The backend authenticates through the documented native Auth Module API, checks fresh central scoped contact, and serializes each derived identity with the installed PostgreSQL locking provider. The central customer workflow is stored/idempotent with an eight-hour execution retention window. Transaction IDs contain no colon because the installed storage key format uses colon separators. Native customer operation metadata remains durable independently of the execution retention window.

Before starting a create, the backend reads persisted executions for the reserved operation. An unfinished/failed execution stays pending and is not automatically resumed. A completed execution is revalidated against current native identity/customer links. Explicit reconciliation uses a distinct no-create workflow, and proof is checked again after waiting for the lock. Duplicate HTTP delivery therefore cannot start parallel customer creation. The PostgreSQL provider is selected explicitly by the bridge and configured as default only during this private enrollment; its package migrations/permissions require review before live activation.

An SDK failure before any HTTP dispatch has a trusted local not_started classification. Only that winning create attempt may release its reservation to reserved for a later explicit attempt. A network/response uncertainty remains fenced. Failed reconciliation cannot release an older uncertain create. This avoids both uncontrolled creation retries and a permanently pending profile caused solely by a missing local service credential.

## Staging credential source and limits

The web runtime now composes the real client and creative mapping journal when the separate private transport flag is explicitly enabled. Its current staging credential adapter reads a privately supplied short-lived service ID token, filters audience/expiry and fails closed when unavailable. It does not verify Google's signature locally or grant access from parsed claims; the private platform ingress performs that verification. It does not accept an incoming browser token/header. No live token is present or generated by this work. Renewable workload-identity acquisition, actual invoker bindings and runtime credential renewal remain an operational integration/review gate; this staging input is not a production credential strategy.

Customer bearer issuance/custody and owned-resource HTTP reads were not implemented by this original provisioning slice; they are now covered by [ADR 0014](ADR-0014-M1b-Customer-Credentials-and-Owned-Reads.md). The browser-facing commerce endpoint still returns only mapping state, never native identifiers, central tokens or service credentials.

## Verification and rollback

107 combined unit/config tests pass. Creative PostgreSQL 16.12 passes 22 scenarios, including exact pre-dispatch release and preservation of older uncertainty. The actual compiled native module test migrates a separate disposable PostgreSQL database, configures the provider/PostgreSQL locks locally, and exercises the real SDK, source router/validator/controller, Auth Module, workflow persistence and customer services. Three duplicate deliveries produce one customer and one execution record. Invalid proof, browser origin and identity override are denied; a seeded unfinished execution creates nothing. Both labeled databases and the loopback HTTP listener are removed. Real platform IAM is explicitly NOT_TESTED.

The optimized Next build and affected type/lint checks pass. Live settings, source publication, fresh npm ci, remote CI, active account-browser SSO and actual staging acceptance remain open. Rollback disables private transport/identity enrollment and restores the previous application/configuration while retaining uncertain mappings, native operation markers, execution/revocation evidence and keys needed for reconciliation. Never delete customers, reset uncertain creates, weaken IAM/TLS or fall back to legacy/email-based identity matching.
