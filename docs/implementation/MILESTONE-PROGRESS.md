1. **M2 Cloud Run remote-staging approval.** `apps/medusa/scripts/remote-staging.mjs`'s `validateApproval()` hard-caps the window at `end <= Date.parse("2026-10-24T23:59:59Z")` — a ceiling baked into the *code*, not just `apps/medusa/scripts/remote-staging-policy.json`. Since real wall-clock time is now past Oct 24, `validateApproval(actualPolicy)` always throws `REMOTE_APPROVAL_EXPIRED_OR_INVALID`, which fails `scripts/tests/medusa-staging.test.mjs`'s `"bundled activation matches the sealed implementation..."` test (`npm run test:staging` / `npm test` / `npm run verify`).
2. **M1b CI source exception.** `scripts/security/m1b-source-policy.mjs` (added in PR #10) gates an analogous, separately time-boxed exception the same way. Once the primary `npm run security:audit` evaluation is not accepted, it falls through to the M1b path and fails with `M1B_APPROVAL_EXPIRED_OR_INVALID`.

**Why this note exists instead of a fix:** renewing either requires (a) a human with real GCP access to check whether `vynvori-medusa-staging` (project `lucky-little-devil`, region `us-east1`) is still actually running, then either decommission it and flip `STAGING_IMPLEMENTATION_COMMIT` in `scripts/security/run-audit.mjs` to `"UNACTIVATED"`, or (b) get fresh founder approval for a new window — a new `notBefore`/`expiresAt` in both policy JSONs, a bumped ceiling constant in `remote-staging.mjs`, and the matching M1b policy renewal. Both are real infrastructure/authorization decisions, not something a coding agent should do unprompted: this repo's own rule is explicit — *"A coding agent must not change founder-approved scope to make a test easier"* (`docs/technical/20-acceptance-matrix.md`) — and forging either approval would be worse than the red CI it would hide.
