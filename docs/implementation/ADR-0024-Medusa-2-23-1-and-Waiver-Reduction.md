# ADR 0024 — move Medusa 2.21.2 to 2.23.1 and reduce the dated waiver to esbuild

2026-11-27. Status: **proposed**. The founder authorized the upgrade in the project thread on 2026-11-27 ("Lets do medusa upgrade first"). For the three open questions this ADR raised (esbuild after the ceiling, the test-coverage change, the Medusa Cloud plugin), the founder delegated the decision to the coordinator on 2026-11-27 ("For the three decisions, I am delegating the authority to you. Do what you think best"); the coordinator's decisions are recorded in Decisions 3, 4 and 8. It is not accepted until the founder merges. Amends [ADR-0020](ADR-0020-Dated-Dependency-Advisory-Waiver.md) and [ADR-0023](ADR-0023-Waiver-Policy-Refresh-and-Next-16-4-6.md); supersedes the Medusa 2.21.2 pin approved in M2 ([ADR-0003](ADR-0003-M2-foundation.md)) for current code. Base: `main` at `147b529`. Scope: project file `triage-20261127/Medusa-2.23.1-Upgrade-Scope.md`.

## Context

Three of the four advisories that the ADR-0020 waiver still accepts come from Medusa 2.21.2's exact pins: glob 13.0.6 (GHSA-3g3m-2fjr-6pw4), minimatch 10.2.6 (GHSA-g3hv-75wg-m249) and i18next 23.7.11 through `@medusajs/dashboard` (GHSA-6jcc-5g8w-32mx). The waiver ceiling is 2026-12-17T23:59:59Z, after which `security:audit` fails closed. Medusa 2.23.1 (latest, released 2026-11-26) pins glob 14.0.2 and i18next 27.1.1. The fourth advisory, esbuild 0.18.20 (GHSA-67mh-4wv8-2f99), comes from drizzle-kit 0.31.11's `@esbuild-kit` loader and has no safe drizzle-kit move; it is out of scope.

Release notes read for this step: 2.22.0, 2.22.1, 2.22.2, 2.22.3, 2.22.4, 2.22.5 (deprecated), 2.22.6, 2.22.7 and 2.23.1 on GitHub, and the Medusa 2.23.0 upgrade guide (the 2.23.0 GitHub release page could not be fetched from the authoring session). No 2.21.3 exists on npm.

## Decision

1. **Versions.** `@medusajs/cli`, `@medusajs/framework`, `@medusajs/medusa` (apps/medusa and the root dev dependency) and `@medusajs/js-sdk` (packages/commerce) move to **2.23.1**. `@types/express` moves 4.17.21 → **5.0.6** (Medusa now runs Express 5.3.0). `react`/`react-dom` move 19.3.0 → **19.3.1** in `apps/web` and the root overrides, because `@medusajs/medusa` 2.23.1 declares a `react-dom ^19.3.1` peer and the upgrade guide forbids a stale override that would hold a second React. No other `apps/web` dependency changes.
2. **Root overrides re-baselined.**
   - `@opentelemetry/instrumentation-pg` 0.75.0 → **0.78.0** (`@medusajs/deps` 2.23.1 requires `^0.78.0`; 0.78.0 is the latest release).
   - `react`, `react-dom` → 19.3.1 (above).
   - **Removed** `bullmq@5.13.0 > uuid 11.1.1`. Medusa 2.23.1 uses BullMQ 6.7.6, which has no uuid dependency and calls `node:crypto` `randomUUID`; a keyed override for BullMQ 5.13.0 can never match again. No uuid package is installed anywhere in the tree.
   - **Removed** `postcss-selector-parser` 7.1.6. The package is no longer in the tree (it came in with the Tailwind 3 admin toolchain, which Medusa replaced with Tailwind 4). An override for an absent package is inert; if the package comes back at a vulnerable version, `security:audit` rejects it as an unwaived advisory.
   - Unchanged: `lodash` 4.18.1, `@graphql-tools/utils` 12.0.4, `@rushstack/node-core-library@5.13.0 > ajv` 8.20.0 (Rushstack 5.13.0 is still installed), `zod` 4.6.7 (Medusa 2.23.1 pins the same version).
3. **Waiver policy** (`security/dependency-waiver-policy.json`, its anchor `WAIVER_POLICY_SHA256` and `scripts/security/dependency-waiver-policy.mjs`): the glob, minimatch and i18next waivers are **removed**; the esbuild waiver keeps the same node, version, `resolved`, `integrity` and development context. `amendmentRecord` points to this ADR and `previousAmendmentRecord` to ADR-0023. Authority, scope, `approvedOn`, `notBefore`, the policy-level `expiresAt` and the global code ceiling **2026-12-17T23:59:59Z are unchanged**.
   - **esbuild per-entry extension (coordinator decision under the founder's delegation, 2026-11-27).** The esbuild waiver alone is extended to **2027-02-28T23:59:59Z**, with a **re-triage by 2027-02-15**. Scope: development only, reached through drizzle-kit's `@esbuild-kit` loader, used only by `drizzle-kit generate` and `drizzle-kit check`; this repository never starts or exposes an esbuild dev server, which is what the advisory affects. Reason: no stable drizzle-kit release drops `@esbuild-kit`, so there is no safe dependency move. Every other waiver rule and the gate's behaviour are unchanged, and no other advisory can use the extension.
   - **How it is enforced.** The global ceiling is hard-coded, so it was not moved; the extension is per entry instead. A code-frozen map `WAIVER_EXTENSIONS` lists exactly one entry: `GHSA-67mh-4wv8-2f99`, expiry `2027-02-28T23:59:59Z`, re-triage `2027-02-15`, node `node_modules/@esbuild-kit/core-utils/node_modules/esbuild`. A policy waiver may carry `expiresAt` and `retriageBy` only if its GHSA is in that map, both values equal the map exactly, its node paths equal the map's (no extra, missing or duplicated node) and every node is development context; otherwise `WAIVER_EXTENSION_INVALID`. Any waiver without a valid extension expires at the global ceiling. After the ceiling, an expired waiver stays in the file but covers nothing: a finding under it is `WAIVER_EXPIRED_OR_INVALID_TIME` and its nodes are no longer required by the completeness check. With no waiver active, the gate rejects exactly as it did at the old whole-policy expiry, even for clean audits. The gate output now reports `waiverExpiries`, the earliest expiry in use as `expiresAt`, and `retriageDue` (informational; lists esbuild from 2027-02-15 without changing the verdict). Editing the JSON alone cannot add an extension or move a date: it breaks the anchor, and behind the anchor the shape rules reject it.
   - The audit fixture `security/fixtures/dependency-waiver-audits.json` is re-captured from real `npm audit --omit=dev --json` and `npm audit --json` output on the final tree.
4. **New Medusa default kept out (coordinator decision under the founder's delegation, 2026-11-27: disabled is the default until the founder opts in).** Medusa 2.23 loads `@medusajs/cloud` as a default plugin even when self-hosted: it adds `/admin/cloud/announcements` and `/admin/cloud/announcement-preferences` routes (the first one calls `https://api.prod.medusajs.cloud` when no URL is set), a cloud table migration and an RBAC policy script. `apps/medusa/medusa-config.ts` disables it with the documented `{ resolve: "@medusajs/cloud", options: { disabled: true } }` entry, which restores the 2.21.2 plugin surface (only `@medusajs/draft-order`). Medusa adds the Audit module only on Medusa Cloud or with a licence, so it is not loaded here. No other default module changed between 2.21.2 and 2.23.1. Enabling the plugin later is a founder opt-in, with its own review of the egress to `api.prod.medusajs.cloud`, the cloud migration and the RBAC script.
5. **Security-lane version pins.**
   - `scripts/medusa-runtime-inventory.mjs` (container job): asserts 2.23.1. Vite 8 bundles with Rolldown, so `@rollup/rollup-linux-x64-gnu` and `@napi-rs/lzma-linux-x64-gnu` left the tree; the native-binding check now loads `@rolldown/binding-linux-x64-gnu` and `msgpackr-extract`, and loads `lightningcss` through `vite`, because the production lightningcss copy is nested under vite.
   - `scripts/security/m1b-source-policy.mjs`: one constant `M1B_MEDUSA_VERSION = "2.23.1"` replaces the three literals used by diagnostic collection, the metadata check and the proposal. The sealed 2026-10 M1b policy JSON (UNACTIVATED, expired 2026-10-24) still records 2.21.2 and is rejected either way.
   - **Left unchanged on purpose:** `scripts/security/audit-policy.mjs` line 141 and `security/m2-exception-policy.json`, `security/m1b-source-ci-policy.json`, `security/pr5-local-preparation-policy.json`, `security/fixtures/pr5-reviewed-runtime.json` and `docs/implementation/evidence/*`. These are sealed historical approvals and evidence (all expired; ADR-0020 keeps them as fallbacks that reject). Editing them would break their anchors or rewrite history. They describe what was approved for 2.21.2, not the current tree.
6. **Historical M2 policy regression input.** `scripts/tests/security-policy.test.mjs` replays the sealed M2 evaluator against the PR4 baseline (`259d388`). It took workspace files from Git but third-party manifests from the live install, which worked only while the live tree still held the 2.21.2 dependency chain. That is no longer true. The third-party manifests for the 82 locations the evaluator reads are now captured once from a real `npm ci --ignore-scripts` of the baseline lockfile (`security/fixtures/m2-historical-install.json`, reproducible with `scripts/tests/capture-historical-install.mjs`); the capture is bound to the baseline commit and to the policy's lock hash. The captured state was checked equal to a snapshot of the full real install (installed manifests, 163 resolutions, 163 ancestry edges, lock hash). All 25 assertions of that test are unchanged.
7. **Tests.**
   - `scripts/tests/dependency-compat.test.mjs`: the BullMQ/uuid case now asserts BullMQ 6.7.6 declares no uuid dependency, no shipped BullMQ file imports `uuid`, its job-id helper is `node:crypto` `randomUUID` and yields v4 UUIDs, and no installed uuid copy anywhere is below the patched 11.1.1. This keeps the original guarantee (no uuid below 11.1.1 reachable from BullMQ) without the override.
   - `scripts/tests/dependency-waiver-policy.test.mjs` is rewritten for the esbuild-only set and the per-entry extension (28 cases; see Consequences for the coverage change). The extension cases cover: accepted from the floor through 2026-12-17T23:59:59Z, 2026-12-18 and up to 2027-02-28T23:59:58Z; rejected at 2027-02-28T23:59:59Z and after; `retriageDue` empty before 2027-02-15 and listing esbuild from then; after the global ceiling, any other advisory, a returning removed advisory and a high esbuild record are still rejected; an entry without the extension, a different date or another GHSA expires at the global ceiling; a synthetic two-entry set keeps only the extended entry active after the ceiling; thirteen JSON edits (later or earlier date, changed or missing re-triage, missing expiry, production context, extra, duplicated or moved node, a second GHSA carrying the extension, and non-string dates) are each rejected; prototype-key and non-string GHSA values are rejected and never reach the map; and clean audits after the extension ends are rejected.
   - `apps/medusa/tests/config.test.ts`: the resolved config contains no `@medusajs/cloud` plugin, still contains `@medusajs/draft-order`, and keeps the admin disabled.
   - `scripts/test-medusa.mjs` (CI `db-integration`, real Medusa boot): five Express 5 boundary cases. Medusa rewrites the `"/*"` foundation matcher to `"/{*splat0}"`; nested, trailing-slash and percent-encoded Store writes and the unenrolled bridge route must still get 403, and `GET /store/regions` must still pass the boundary (200).

8. **Coverage change accepted (coordinator decision under the founder's delegation, 2026-11-27), with two conditions, both met.** (a) The saved 2.21.2 install snapshot is integrity-pinned: `HISTORICAL_INSTALL_SHA256` is checked in the test before the snapshot is used (Decision 6, review LOW-2). (b) The checks no test can reach stay in the code and are documented here with the reason: `FULL_AUDIT_NARROWED` and `ADVISORY_GRAPH_CHANGED` (Consequences), and the multi-entry guards of the extension (below).

## Lockfile summary

Generated with `npm install` after removing only the `@medusajs/*` lock entries (a plain install hit `ERESOLVE` against the 2.21.2 entries). Compared as resolved package sets, not lines: 1,264 → 1,247 entries; 499 `name@version` added and 533 removed (340 packages changed version, 151 new names, 160 names gone, mostly Rollup → Rolldown, Babel, Tailwind 3 tooling and `uuid`). Every non-bundled entry resolves to `https://registry.npmjs.org/` with an integrity hash; the six entries without one are `inBundle` files inside the registry tarball of `@tailwindcss/oxide-wasm32-wasi` (the same pattern already exists for its 4.3.3 copy). No new package with an install script; `@medusajs/telemetry` and `msgpackr-extract` only moved versions. `npm ci` followed by `npm ls --all --omit=optional` is clean.

## Consequences

- `npm run security:audit` → `ACCEPTED_WITH_DATED_WAIVER` with **0 production findings** and 4 full-audit findings (esbuild and its three dependents `@esbuild-kit/core-utils`, `@esbuild-kit/esm-loader`, `drizzle-kit`), all moderate. Before: 61 production and 65 total.
- The waiver now covers one development-only advisory. The 2026-12-17 global ceiling still stands for every waiver except esbuild, which runs to 2027-02-28T23:59:59Z (Decision 3). Re-triage by 2027-02-15: move drizzle-kit if a stable release drops `@esbuild-kit`, otherwise a new decision is needed before 2027-02-28, when `security:audit` fails closed again.
- **Test coverage change, for reviewers to accept explicitly.** With no production waiver left, any production finding is rejected (`UNWAIVED_ADVISORY`, `UNWAIVED_VULNERABLE_NODE` or `DEVELOPMENT_NODE_IN_PRODUCTION_AUDIT`) before the evaluator's superset comparison, so `FULL_AUDIT_NARROWED` joins `ADVISORY_GRAPH_CHANGED` (since ADR-0023) as defence in depth that no test can reach. The test proves that a production finding missing from the full audit is still rejected. Production-side cases (new advisory, high or critical record, development waiver at a production node, return of the glob, minimatch, i18next and Next.js advisories) inject a record at a synthetic production node. Mutation check of the evaluator: neutralising each of the other 20 rejection codes checked fails at least one test; `AUDIT_INCOMPLETE` needed a new precise case, which is added. A second mutation pass on the extension logic (16 mutants: expiry lookup, boundary `<` vs `<=`, each of the seven extension shape rules, the re-triage flag, the reported expiry, the none-active rejection) is killed by at least one test, with four exceptions: one equivalent mutant (a redundant `hasOwn` test, since removed) and three guards that only a policy with more than one entry can reach, because with the one-entry policy "no entry active" already rejects at the top: the `WAIVER_EXPIRED_OR_INVALID_TIME` code for a finding under an expired entry, the completeness check over active entries only, and the lookup over active entries only. They stay as defence in depth for any future multi-entry policy; the decision they depend on (`activeWaivers`, `waiverExpiry`) is tested directly on a synthetic two-entry set.
- The historical M2 regression test no longer reads the live install (Decision 6).
- Express 5 runtime behaviour is proven only by CI (`db-integration` Medusa boot and the `container` job). It is NOT_RUN in the authoring sandbox (no Docker, no Postgres).

## Rollback

Revert the commits and run `npm ci`. Medusa 2.21.2, the old overrides and the four-waiver policy return, and `security:audit` accepts again under the 2026-12-17 ceiling, with no per-entry extension. To withdraw only the esbuild extension, remove `expiresAt` and `retriageBy` from the entry and re-anchor; the esbuild waiver then expires at the global ceiling. There is no persistent Medusa database and no Redis, so nothing has to be downgraded in place. If a future environment has run 2.23.1 against a Medusa database, restore that database from the backup taken before the upgrade rather than running 2.21.2 against migrated tables.
