# ADR-0003 — Isolated M2 service foundation

2026-10-15. Status: implemented locally; independent review and infrastructure acceptance pending.

M1a found unsafe identity linking, product binding, session and provisioning behavior. M2 must support a future corrected bridge without activating it. Medusa Cloud supports npm monorepos and deploys `.medusa/server`; backend configuration must be self-contained. Its documented npm React overrides are aligned to the existing web versions.

Use a dedicated `apps/medusa` backend with native commerce ownership, no customer auth providers, no customer auth routes and no Store writes. Admin API retains native user authentication; Admin UI is disabled for M2. No custom TCM provider, catalog seed, payment configuration, customer provisioning or event consumers. Configuration validates a separate database, exact CORS origins and separate strong secrets. Native Medusa migrations run only against that database.

`packages/db` owns one additive `vynvori_infrastructure.synthetic_probes` table in a distinct creative PostgreSQL database. Drizzle uses a bounded `pg` pool and tracked SQL migrations. No identity/ledger/outbox/production tables until their milestone. The default database name is deliberately restrictive; staging requires a pinned Neon pooled hostname and verified TLS. This is accidental-misconfiguration defense, not proof of cloud ownership: an operator must verify project/branch/role scope before supplying credentials.

`packages/commerce` contains server-only Medusa liveness, private R2 fixture storage and processing readiness adapters. It has no commerce mutation/identity API. Deep diagnostics run in an operator CLI; the M0 public health contract is unchanged. Readiness v1 distinguishes unconfigured/unavailable/ready and redacts upstream failures. Medusa health proves liveness only, not catalog or DB acceptance.

The dependency-free worker accepts only versioned synthetic dry-run requests. Local requests require an application token; deployment also requires Cloud Run IAM, explicit invoker, internal ingress and a dedicated identity. The adapter supplies a short-lived Google ID token through `X-Serverless-Authorization`, separately from the app token. This template requires a trusted internal caller/network path; direct Vercel access is not enabled. No image URLs or private art are accepted. M5 adds rendering after separate authorization.

Security review: CORS does not authorize callers; customer endpoints and Store mutations are explicitly denied. No bearer/Admin secret reaches a browser. Private bucket policy, cloud identity/resource ownership and actual authenticated Cloud Run ingress remain external gates. Storage uses conditional immutable writes, exact fixed PNG/size validation and integrity checking; it is not a general upload or image-sanitization implementation. Unknown storage PUT outcomes are not retried automatically. The smoke CLI reports unavailable if cleanup fails, so operators must reconcile the synthetic run before retrying.

API changes: native-authenticated Medusa `GET /admin/m2-readiness` exercises the product query/database and returns only readiness v1, never product data. Worker `GET /health`, authenticated `GET /ready`, authenticated `POST /v1/dry-run`; version 1 accepts only `{version:1, fixture:"m2-synthetic-v1", requestId:UUIDv4}` and returns deterministic checksum/status/`printed:false`. Errors are sanitized 400/401/404/413/415. No new Next.js API, cross-system events or commerce writes. Duplicate valid dry-runs have identical results and no persisted effect.

Rollback: keep features OFF; revert code to the prior reviewed release. Preserve additive synthetic schema and migration history by default. If removal is needed, back up the isolated creative database with verified `pg_dump`, confirm no other consumers, then review a separate forward migration; never modify applied SQL or run a generic down/drop against shared databases. Medusa rollback follows its native migration/backup process and version-compatible prior application artifact. Do not downgrade its database blindly. Worker rollback selects the previous private revision/image digest; keep invoker/IAM controls. No production migration or remote deployment occurred in this milestone.

Alternatives rejected: shared Lucky commerce/resources, email linking, full speculative domain schemas, public worker, root orchestration framework and restoring historical workspaces. These conflict with isolation or extend scope. Real cloud acceptance is separately recorded in [M2](M2.md).
