# ADR-0021 — M7 credit-ledger core: foundation (S1)

Status: **proposed, implemented locally for S1 only; not deployed.** Base commit `1fa10e8551211a3ad8611074634773a3f5125b34`. Branch `claude/youthful-johnson-p85ycz`. Plan: `docs/implementation/M7-Plan.md` (rev 4), step S1. Founder approved S1 on 2026-11-02 (direct instruction in session). This ADR records the plan's design decisions as the contract that S2–S9 implement; S1 itself ships **no tables, no wallet or quote logic, no workflows and no dependencies**.

## Context
M7 needs a Neon/Drizzle credit ledger (whole-number credits; `available` / `reserved` / `held_for_review` buckets; append-only entries; versioned quotes; reserve → settle/release; reconciliation hold on unknown provider outcome). Medusa stays the system of record for commerce and is never written from Drizzle. Every financial/paid flag stays OFF; no price, credit cost, package size, hold duration or cut-off may be invented. S1 lays the verified foundation: this ADR, a hash-pinned migration journal with a tested rollback, additive server-only contracts, and the per-file Postgres test harness.

## Decisions (D1–D15; final wording is the plan's §5, which S2–S9 implement)
- **D1 Actor key.** `wallets.user_id uuid PRIMARY KEY REFERENCES vynvori_identity.profiles(id) ON DELETE RESTRICT`; every owned row carries `user_id`. No guest wallets, no email column, no Medusa customer id.
- **D2 Buckets and balanced entries.** `available/reserved/held_for_review/consumed` as `bigint CHECK (>= 0 AND <= 9007199254740991)`; every entry has five deltas summing to zero with a per-`entry_kind` sign pattern (`grant`, `reserve`, `release`, `settle`, `hold`). `0 < charge ≤ hold`. Hold-resolution kinds and anything entering or leaving `operator_remedy` are deferred to the remedy milestone.
- **D3 Database-enforced immutability.** `ledger_entries` append-only (triggers); wallet and reservation state change only through the entry trigger (guard: `pg_trigger_depth() > 1` AND current user = owner of the `SECURITY DEFINER` apply function — see the S2 addendum; the depth check alone is bypassable); unique cause `(cause_kind, cause_ref)`; one of release/settle/hold per reservation. **Binding for S5:** the reservation-state guard (and every other guard protecting state that a trigger writes) must use the same pattern as the wallet guard — a `SECURITY DEFINER` writer function, a guard that requires `current_user` to be the *owner of that writer function* (compared by name via `pg_get_userbyid`, never a `regrole` cast), `pg_trigger_depth() > 1`, and a trigger-context check (`TG_RELID`, `TG_OP`, `TG_WHEN`, `TG_LEVEL`) in every trigger function. `pg_trigger_depth()` alone is never a sufficient guard: executed bypass — a trigger on a role-owned `TEMP` table fires at depth 1, so its nested `UPDATE` sees depth 2.
- **D4 Idempotency.** Immutable `ledger_commands`; `UNIQUE(scope, idempotency_key)`, `scope = {user_id}:{command_kind}`; same key + same hash replays, different hash is `IDEMPOTENCY_CONFLICT`; terminal business rejections are persisted under the key, transient failures are not. The contract envelope (S1) encodes the scope rule and key format.
- **D5 One reservation per provider operation**, bundle allocations frozen in the quote; the ledger verifies and never computes a split or rounding remainder.
- **D6 Release, settle and hold are evidence-gated and never auto-resolved.** Settle needs `persisted_delivered` with verified manifest and owner/rights; release needs `verified_zero_charge_failure` only (no pre-dispatch release — founder question Q9); hold needs `outcome_unknown` or `persistence_failed_under_review`. A vendor-charge message is never evidence. No timer or sweeper.
  **S5/S6 GATE (carry-forward):** the evidence in S1 is caller-asserted and forgeable (`hasVerifiedManifestHash: true` and `ownerAndRightsVerified: true` are literals a caller can type). S5/S6 must replace the booleans with values the ledger compares to persisted rows (`manifestSha256` against the stored manifest, `reservationId`, owner read from the database) and accept evidence only from `system` actors through `LedgerInternalCommandV1Schema`. Parse success is never authorization.
- **D7 Quotes.** Immutable `ledger_quotes` with `UNIQUE(quote_id, version_no)`, a locked lineage pointer, authorization checks in one transaction ending in a default-deny `AuthorizationEligibilityPort`. Column ↔ contract mapping:

  | Column | Contract field |
  |---|---|
  | `max_charge_units` | `maxHoldUnits` |
  | `credits_quoted` | `creditsQuoted` |
  | `price_version` | `pricePolicyVersion` |
  | `operation_kind` | `offerKind` |
  | `model_ref` | `modelQualificationSnapshotId` for finals; for bundles the concept-model snapshot reference **supplied by the issuer** (the bundle contract has no model field — additive note for S3) |

  `LedgerQuoteRecordV1` uses the column-side names and stores the validated `QuoteViewV3` separately.
- **D8 Promo uniqueness** per verified `issuer + subject`; entitlement, not a wallet debit; evidence-gated events.
- **D9 Packages and refinement slots** (scaffolding), including the C-02 reopen rule via root's guard.
- **D10 Locking and outcomes.** Lock order: lineage → wallet → reservations by `id`; transaction-scoped features only (Neon pooled connections); `LEDGER_OUTCOME_UNKNOWN` is resolved by replaying the same key.
  **Outcome classification — the binding rule (S2 wording).** *Before `COMMIT` is sent:* an error that carries a SQLSTATE **and** severity `ERROR` is a **definite** rollback in every SQLSTATE class (including 57014 statement timeout/cancel and any server-reported 08xxx `ERROR`); an error with no SQLSTATE or no severity, any `FATAL`, and the driver's own client-level failures ("not queryable", "Client was closed", "Connection terminated") are `LEDGER_OUTCOME_UNKNOWN`, in every phase, because the client cannot know what the server did. *While `COMMIT` is in flight:* definite only for severity `ERROR` in SQLSTATE classes 23 and 40 (one deliberate tightening: 40003 `statement_completion_unknown` is by definition unknown and is never definite); everything else is `LEDGER_OUTCOME_UNKNOWN`. The classifiers are pure, exported and tested per branch. They rely on the server's English severity string: an unrecognised locale degrades to `LEDGER_OUTCOME_UNKNOWN`, never to a wrong "definite".
  **Two different kinds of "unknown".** A `COMMIT`-time failure is a *database-transaction* failure whose true state is unknown to the caller; it is resolved by replaying the same idempotency key. That is different from a *provider-outcome* "unknown", which creates a reconciliation hold, is never auto-resolved and never retried.
  **Further carry-forwards:** the ledger must compute `contentSha256` / `requestSha256` itself and never trust a caller-supplied value; a zero-credit quote is legal only for the promo kind (no allocations) and S3 must enforce `max_charge_units > 0` for every other kind; an `EligibilityDecisionV1` is bound to a single inline call and must never be cached.
- **D11 Ownership.** Every predicate carries `user_id`; absent and foreign ids return the same `NOT_FOUND`; internal transitions carry `actor` + `expectedUserId`.
- **D12 Funding in W1: a grant-source registry, not a flag.** `0002` registers no sources; the runtime role gets no `INSERT` on the registry, so runtime privileges alone cannot mint credits.
- **D13 Not reachable from runtime.** Static test from S2: nothing under `apps/` and no non-test module imports `@vynvori/db/ledger*`; no numeric constants exported; flags all `false`. S1 satisfies this trivially (no ledger code is imported anywhere).
- **D14 Read-only checks** (`checkWalletInvariants`, `findOrphanedReservations` with a required cut-off, report-only).
- **D15 Test databases and connection budget** — recorded below.

## Connection budget (D15)
Each ledger test file owns database `vynvori_m7_<name>_test`; the fixture allow-list currently contains `migrations`, `fixture`, `concurrency`, `core`, `privileges` (later steps append). The single 100-way file `ledger-concurrency.test.ts` (from S2) may use up to **110** connections; every other ledger file caps its pool at **5** (≤ 9 files ⇒ ≤ **45**). Existing suites, counted at their declared maxima in the repository: `auth-state.test.ts` 6, `composition-pg.test.ts` 4, runtime pools in `packages/db/src/{index,identity}.ts` 3 + 3 = **16**. Pools alone give 110 + 45, but each DB-using file also holds one persistent client and one transient admin/probe connection, so the worst case is about **112** for the concurrency file plus **7** for each of the 9 other DB-using files (**63**) = about **175**, plus **16** for the existing suites = about **191**, below `250 − 3 reserved superuser slots = 247` (CI sets `max_connections=250` and asserts it in `.github/workflows/m2.yml`, root-owned). The fixture reads `SHOW max_connections`; `ledgerPool` clamps to `max_connections − 3` and reports `degraded` when the server limit is below the requested cap. It clamps a **single** pool and cannot see other files' usage; if the sum ever approaches the limit, root may serialize the Postgres suites with `--test-concurrency=1`. From S2 the concurrency file must **fail** under `CI_REQUIRE_PG_TESTS=1` when degraded; locally it runs reduced and its 100-connection row is `NOT_RUN`. Measured in CI by S9, not by S1.

## Test harness semantics
Postgres-backed tests gate on `M7_TEST_POSTGRES_URL` or `M2_CREATIVE_DATABASE_URL`. URL present ⇒ run. Absent and `CI_REQUIRE_PG_TESTS=1` ⇒ the test **fails**. Absent otherwise ⇒ skipped, reported `NOT_RUN`, never PASS. `CI_REQUIRE_PG_TESTS` is deliberately not a `VYNVORI_*` variable (`packages/shared` rejects unknown `VYNVORI_*` keys). The fixture refuses any target that is not `127.0.0.1` + user `synthetic` + an **explicit port** (only `5432`, CI's value, unless `M7_TEST_POSTGRES_PORT_ACK` names exactly the port used by a local throwaway server) + no query string or fragment + an allow-listed `vynvori_m7_<name>_test` database. On the maintenance connection, **before any `DROP`/`CREATE DATABASE`**, the fixture asserts server-side that `current_user = 'synthetic'` **and** `current_setting('is_superuser') = 'on'` (CI's `synthetic` is the bootstrap superuser — the `foundation` job already runs `ALTER SYSTEM SET max_connections` as it — whereas managed databases normally give application roles no superuser); it is exercised by the CI Postgres test and unit-tested for wrong user and non-superuser. The server **address is deliberately not checked**: an earlier revision asserted `inet_server_addr()` is loopback, which failed in CI because the Postgres service is a Docker container reached through a published port, so the server sees the container-side address rather than `127.0.0.1`. **Residual risk:** a loopback SSH tunnel to a remote server on which `synthetic` is a superuser still passes these checks; the blast radius is confined to the allow-listed database names (and the auth DDL applied inside them).

### Security-review dispositions (S1)
Fixed in S1: fixture target guard now rejects any URL query/fragment (pg lets `?host=`/`?user=` override the authority) and never echoes a malformed URL; the down script's guard and drops are one atomic statement (safe under plain `psql -f`); user ids must be lowercase UUIDs so case variants cannot fork idempotency scopes; quote `expiresAt` must follow `issuedAt`. Carried forward: settle/release/hold evidence parse success is **not** authorization — S5/S6 must bind it to persisted state read by the ledger and restrict it to `system` actors (S6 gate); `FORBIDDEN_PUBLIC_FIELDS` now also lists `requestSha256`, `evidenceRef`, `modelRef` and `contentSha256` (root-granted additive edit, none is used in a public shape on `main`). `capabilitySnapshotId` is deliberately **not** listed: it is a public field (`quote.ts`, `studio-plan.ts`), and it stays out of customer projections only because `ledger-internal.ts` is `server-only` and absent from the public barrel (tested). Concurrent runs of the same test name on a shared server would drop each other's database (CI uses a private server per job).

## Rollback
- Code: revert the PR; the ledger is unreachable from runtime.
- Data: `rollback/0001_ledger_schema.down.sql` (manual; guarded). It refuses while any relation exists in `vynvori_ledger`, drops `vynvori_ledger`, then drops the journal schema `vynvori_ledger_migrations` so up → down → up does not trip the drift check. Rollbacks apply in reverse numeric order. **Caveat (not hidden):** once later migrations add append-only tables, deleting rows needs a superuser to disable triggers; removing real ledger data is **restore from backup**, not "run the down script".
- **Half state (manual path):** if the journal schema `vynvori_ledger_migrations` exists but `vynvori_ledger` does not (an interrupted manual run), the down script reports `schema not present` and the runner reports `HISTORY_OR_SCHEMA_DRIFT`. An operator confirms with `SELECT current_database()` that the target is disposable or backed up, checks `\dn vynvori_ledger*`, and runs `DROP SCHEMA vynvori_ledger_migrations CASCADE;` by hand (nothing else lives in it), then re-applies. The down script takes the runner's advisory lock `(742110, 7)`, sets `lock_timeout`, and schema-qualifies its catalog references.
- Tested: up → down → up, rollback refusal while a relation exists, and half-state drift detection in `ledger-migrations.test.ts`.

## S2 addendum — wallet, immutable command log, append-only ledger (migration `0002_wallet_ledger`)
Status: **proposed, implemented locally for S2 only; not deployed.** Plan step: `M7-Plan.md` §7 S2. Nothing in S2 adds a flag, a dependency, a route or a runtime import (static test `ledger-isolation.test.ts`, D13).

**What S2 adds.** Tables `wallets`, `ledger_commands`, `ledger_grant_sources`, `ledger_entries` in `vynvori_ledger`; `packages/db/src/ledger-core.ts` (`ensureWallet`, `getWalletSummary`, `canonicalRequestHash`, `runLedgerCommand`, `appendGrantEntry`, the pure classifiers); the `./ledger-core` export. `0002` inserts **no rows**: no grant source is registered, so after the migration no credit can be created by anyone. No exported function registers a source; the test fixture does it as the superuser and lives in `tests/` only.

**Outcome classification as implemented (D10).** Exactly the binding rule in D10 above. Mapping of definite server errors: class 23 → `DATABASE_REJECTED`; 40001/40P01/55P03/57014 → `TRANSIENT`; otherwise `DATABASE_ERROR`; none records anything under the key. Every statement runs on a connection wrapper that tags driver-originated errors, so a *callback's own bug* (a `TypeError`, a thrown `null`) is a generic `DATABASE_ERROR` without its message, not a database outcome. A connection that produced an unknown outcome is destroyed, never returned to the pool; a pooled client has an `error` listener for as long as it is checked out (otherwise a connection that ends between statements would be an unhandled `error` event that crashes the process). This is a database-transaction uncertainty; it is not a provider-outcome unknown and creates no reconciliation hold.

**Idempotency as implemented (D4).** The ledger computes `requestSha256` itself from sorted-key canonical JSON of the payload (non-finite numbers, unsafe integers, `undefined`, bigint and class instances are rejected). The wallet row is locked `FOR UPDATE` first, so same-user commands serialize there; the command row is then inserted `ON CONFLICT (scope, idempotency_key) DO NOTHING`. Existing row + same hash replays the result reconstructed from `ledger_entries`; different hash is `IDEMPOTENCY_CONFLICT`; the callback never re-runs. `LedgerBusinessRejection` is persisted as a `rejected` command row **in the same transaction under a savepoint while the wallet lock is held** (see *Command-transaction guarantees*; only the codes in `PERSISTABLE_REJECTION_CODES`), replays identically and cannot succeed after a later top-up. `source_ref` uniqueness (`UNIQUE (cause_kind, cause_ref)`) makes a second grant under a *new* key a `DUPLICATE_CAUSE`, not a second grant. Idempotency keys and hashes are never placed in error messages.

**Privilege model B as implemented — binding.** The migration contains **exactly one `SECURITY DEFINER` function**, `ledger_entries_apply_to_wallet()` (the only writer of wallet balances); every other function (`reject_mutation()`, `wallets_insert_guard()`, `wallets_update_guard()`, `ledger_entries_check_command()`) is invoker-rights. Every function pins `SET search_path = pg_catalog, pg_temp` (`pg_temp` last; `vynvori_ledger` is deliberately not in the path; bodies are fully schema-qualified, no dynamic SQL) and gets `REVOKE ALL ON FUNCTION … FROM PUBLIC` — the only `REVOKE` a migration may contain; the migration grants nothing and names no runtime role. `wallets_update_guard` rejects unless **both** `pg_trigger_depth() > 1` **and** `current_user` is the **owner of `ledger_entries_apply_to_wallet()`** (compared by name with `pg_get_userbyid`, null-safe via `IS DISTINCT FROM`; never through a `regrole` cast, which case-folds and parses identifiers). **The real invariant: the guard's only legitimate writer is the owner of the apply function.** The rollout re-owns only the function, so the guard must follow the function, not the table. Under the definer path `current_user` is that owner; a trigger created by any other role runs as that role and is rejected even if the role holds broad write rights such as `pg_write_all_data`. **Direct invocation of the definer function by the runtime role fails both without `EXECUTE` (42501) and with it (0A000, "trigger functions can only be called as triggers"; tested).** **Every trigger function also verifies what fired it** and raises otherwise: the four table-bound functions (`wallets_insert_guard()`, `wallets_update_guard()`, `ledger_entries_check_command()`, `ledger_entries_apply_to_wallet()`) pin `TG_RELID` (by `regclass`), `TG_OP`, `TG_WHEN` and `TG_LEVEL`; `reject_mutation()` is shared by all append-only tables and therefore pins the schema (`TG_TABLE_SCHEMA`), timing, operation and level instead (it can only raise, so it is harmless on any table). So a role that is ever given `EXECUTE` on the definer function cannot attach it to a trigger on its own `TEMP` table and mint credits. *Test coverage:* the `TG_RELID` branch of the apply function is behaviour-tested (`EXECUTE` granted, `TEMP` table); the `TG_OP`/`TG_WHEN`/`TG_LEVEL` branches and the other four functions are covered statically only, and S9 adds behaviour tests for them (hardening, not an escalation risk).

**Evidence from the S2 security review (executed on PostgreSQL 16, independently reproduced).** Three holes were found and fixed: (1) *guard bypass by a TEMP trigger* — a role with exactly model A's grants plus the default `TEMP` privilege created a trigger on its own temp table whose function (in `pg_temp`) updated `wallets`; it fires at depth 1, so the wallet guard saw depth 2 and passed (`available_units` became 1000000 with `revision = 0` and zero entries); the depth guard cannot tell the ledger-entry trigger from any other trigger → fixed by the definer function (the runtime role needs no balance `UPDATE`) and the owner check. (2) *`FOR UPDATE` needs `UPDATE` privilege* (42501 without it) → the runtime role needs **column-level `UPDATE (user_id)` on `wallets` only**; a no-op `SET user_id = user_id` fires the guard and is rejected, so no balance can change; `lockWallet` keeps `SELECT … FOR UPDATE`. (3) *broad write roles defeat a depth-only guard* (`pg_write_all_data`, which a managed-database admin role may include) → the owner check. `ledger-privileges.test.ts` proves all of this as non-superuser roles (CI's `synthetic` is a superuser and would pass any design) and the mutation table below shows which named test fails for each deliberate weakening.

**Binding consequences.**
- **The definer's effective privilege equals the owner's.** The existing staging migration owner is known to be over-privileged (CREATEDB, CREATEROLE, BYPASSRLS; see `M2-Creative-Staging-Plan-20261018.md`). **Rollout stays unauthorized until a dedicated `NOLOGIN`, `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEROLE` role owns the functions (`ALTER FUNCTION … OWNER TO …`), delivered inside the S9 grants proposal for the founder to execute. This is a precondition, not an option.**
- **The S9 grants proposal must include:** a dedicated `NOLOGIN`, `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEROLE` definer owner role; `ALTER FUNCTION vynvori_ledger.ledger_entries_apply_to_wallet() OWNER TO` it; to that role **exactly** `USAGE` on schema `vynvori_ledger` and `SELECT` and `UPDATE` on `vynvori_ledger.wallets` — nothing more (no INSERT, DELETE, TRUNCATE, REFERENCES or TRIGGER), and nothing else the function body touches, because the function touches nothing else. The list is derived from the code by test, not from memory: `ledger-privileges.test.ts` gives a dedicated owner only these three privileges, shows the legitimate `runLedgerCommand` + `appendGrantEntry` path works, then shows it fails with `42501` when any one of the three is removed (so the list is neither missing something nor padded). These grants are executed by the founder in S9, never by a migration; runtime column-level `UPDATE (user_id)` on `wallets` only; `REVOKE TEMPORARY ON DATABASE … FROM PUBLIC` for the ledger database (revoking from the role alone does nothing while `PUBLIC` holds it); **`EXECUTE` on the definer functions is NOT granted to the runtime role, and never through a blanket schema-wide `GRANT EXECUTE ON ALL FUNCTIONS`**; a runtime role that is not the table owner (a runtime role that owns the tables can `DISABLE TRIGGER` and bypass everything, so the owner must be distinct), not a member of `pg_write_all_data` or any managed-database superuser-like role; owner distinct from runtime; and the HARD GATE text below.
- **BINDING S9 precondition — the definer owner has no members and the runtime role cannot `SET ROLE` to it (executed exploit path).** After the re-own step, no role other than the definer itself may be a member of (or able to `SET ROLE` to) the definer owner role: not the runtime role, not the migration login. Executed on PostgreSQL 16: `GRANT <definer> TO <runtime>`, then as runtime `SET ROLE <definer>` and a `TEMP`-table trigger issuing `UPDATE wallets` passes the guard (`current_user` is the function owner, depth 2) and minted — the wallet reached 777 with no ledger entry. S9 must assert this by test after the re-own step (`pg_has_role(<runtime>, <definer>, 'member') = false`, `pg_has_role(<runtime>, <definer>, 'usage') = false`, also for a runtime variant that holds `pg_write_all_data`), and `ledger-privileges.test.ts`'s structural assertion today only covers the pre-re-own table owner.
- **BINDING S9 owner-change procedure (must be executable by the role that will run it).** `ALTER FUNCTION … OWNER TO <definer>` requires the executing role to be a superuser, or to be able to `SET ROLE` to the new owner **and** the new owner to hold `CREATE` on schema `vynvori_ledger` at that moment. On a managed database the executor is not a true superuser, so the procedure is: (1) transiently `GRANT <definer> TO <executor>` and `GRANT CREATE ON SCHEMA vynvori_ledger TO <definer>`; (2) `ALTER FUNCTION vynvori_ledger.ledger_entries_apply_to_wallet() OWNER TO <definer>`; (3) **immediately** `REVOKE <definer> FROM <executor>` and `REVOKE CREATE ON SCHEMA vynvori_ledger FROM <definer>`; (4) assert the end state: the definer holds exactly `USAGE` on the schema plus `SELECT` and `UPDATE` on `wallets`, `has_schema_privilege(<definer>, 'vynvori_ledger', 'CREATE') = false`, and it has no members. The privilege test performs the re-own as the superuser fixture, which hides step 1; S9 adds a test that runs the procedure as a non-superuser executor and asserts the end state. The "exactly" claim is a *minimal necessary* set (each of the three is necessary — removing any one gives `42501`); it does not prove that nothing extra is harmless (e.g. an extra `INSERT` still works; column-level `UPDATE` on the five bucket columns also suffices), so S9 keeps the list as written and treats any additional privilege as a deviation to be justified.
- **HARD GATE.** "No real grant source may be registered by any means (migration, seed, runtime, operator script) before grant writes sit behind a definer command function bound to verified external evidence. Gate for M4 and W3; precondition in the S9 grants proposal." Reason: the runtime role needs `INSERT` on `ledger_entries` and `ledger_commands`, so once any grant source is registered it can mint up to the entry bounds. In W1 no source exists and the runtime cannot create one (no `INSERT` on `ledger_grant_sources`, asserted as a restricted role).


**Other S2 review dispositions.** Fixed (rounds 1–2): rollback now takes `ACCESS EXCLUSIVE` locks on the four tables before the emptiness check (a writer committing between check and `DROP` would otherwise be destroyed silently), pins `search_path` and schema-qualifies catalogs; SQLSTATE `40003` (statement_completion_unknown) is an *unknown* outcome, only `40001`/`40002`/`40P01` and class 23 are definite; `LedgerDb` no longer accepts a bare `Client` (cannot be destroyed, interleaves transactions); the callback's `tx` handle is dead after the command ends; a broken connection after a failed `ROLLBACK` surfaces the original rejection and records nothing; `LedgerError` keeps only `{code, sqlstate, constraint}` (never the raw driver error, which can contain the idempotency key); `mapDefinite` guards non-object throws and never keeps the driver error; cyclic/deep payloads are `INVALID_INPUT`; test pools are created inside `try`; the termination test polls `pg_stat_activity`; an export allow-list test makes any new `ledger-core` export (e.g. another minting path) a deliberate change. Tracked, not fixed here: an entry may reference an earlier-committed applied command (S5's binding trigger must require the same transaction); `ENABLE ALWAYS TRIGGER` against `session_replication_role=replica` (superuser-only, outside the runtime role); `severity` is localised, so CI/fixtures must run an English `lc_messages` (fails safe to unknown); replay order within one command uses `created_at, entry_id` and needs a sequence once a command can write several entries; sums of the four buckets can exceed 2^53-1, so JS must never add buckets.

**Command-transaction guarantees (round 2).** A terminal business rejection is recorded **in the same transaction** under a `SAVEPOINT` while the wallet lock is held (`ROLLBACK TO SAVEPOINT`, insert the `rejected` row, `COMMIT`), so no top-up can slip between the decision and its record; *once a key is recorded, its callback never runs again* (two concurrent same-key commands whose callback rejects run it exactly once). After `BEGIN` every command sets `lock_timeout` (10 s), `statement_timeout` (30 s) and `idle_in_transaction_session_timeout` (30 s) — private technical bounds, not business values (the S1 runner uses `lock_timeout` 4 s); `options.lockTimeoutMs` can only shorten the lock wait. A stalled lock holder makes a waiter fail with `TRANSIENT` (55P03) and release its connection. The idempotency hash binds the **actor kind** plus the payload, and `appendGrantEntry` requires the command's hash to equal the hash of the very entry it writes (actor, source, ref, amount), so an empty or different caller payload cannot record one effect under a key and write another; a hand-built or copied transaction handle is rejected (handles are issued only by `runLedgerCommand`, tracked in a module-private `WeakSet`); the handle is dead after the command ends. Canonicalisation has a node budget and ancestor tracking (cycles and shared deep structures are `INVALID_INPUT`); huge or sparse arrays are rejected by length before iterating. Connection acquisition is inside the error boundary (a failing `connect()` becomes a bare `TRANSIENT` `LedgerError`, never the driver error with host/port), pools are recognised by a `connect` function rather than `instanceof` (a second `pg` copy or a serverless pool works), and the issued transaction handle is frozen.

**Break-glass — operational note, not a code bypass.** After the function is re-owned to the dedicated role, a *superuser that is not the function owner* is blocked by the guard too: it cannot `UPDATE wallets` directly or through a trigger. There is no bypass in the code and none is added. **Re-owning the function back does not by itself permit a correcting `UPDATE`:** the guard also requires `pg_trigger_depth() > 1`, so even the function owner cannot `UPDATE wallets` directly (reproduced). The audited break-glass options are (a) restore from backup, or (b) `ALTER TABLE vynvori_ledger.wallets DISABLE TRIGGER wallets_update_guard` by the table owner or a superuser in a reviewed, time-boxed, audited step, then re-enable it — never a silent `UPDATE`. A table owner that is also the runtime role can do (b) at will, which is why the owner must be distinct from the runtime role.

## S3 addendum — versioned quotes, insert-only lineage anchor, frozen allocations (migration `0003_quotes`)
Status: **proposed, implemented locally for S3 only; not deployed.** Plan step: `M7-Plan.md` §7 S3. Nothing in S3 adds a flag, a dependency, a route or a runtime import (D13, extended below). `0003_quotes.sql` adds no `GRANT`, no `CREATE`/`ALTER ROLE`, no `OWNER TO`; the only `REVOKE` is function-level `FROM PUBLIC`; it adds **no** `SECURITY DEFINER` function — the migration set still keeps exactly one (S2's `ledger_entries_apply_to_wallet()`).

**Design (binding for S3; refines plan D7/D10).**
- Every quote operation (`issueQuote`, `renewQuote`) is a ledger **COMMAND of the quote owner run through `runLedgerCommand`**, which locks the user's wallet row `FOR UPDATE` first (ADR-0021 D10). All of one user's quote operations therefore serialize on that wallet lock. There is **no lineage lock and no mutable lineage pointer**: this replaces plan D10's "lineage" lock step and D7's "mutable pointer table" with the lock order wallet → (later, S5) reservations by id.
- `ledger_quote_lineages` is an **insert-only anchor**: `(quote_id text PRIMARY KEY, user_id uuid NOT NULL REFERENCES vynvori_identity.profiles(id) ON DELETE RESTRICT, created_at, UNIQUE (quote_id, user_id))`, immutable (`UPDATE`/`DELETE`/`TRUNCATE` rejected via `reject_mutation()`, reused from S2 — no new immutability function was needed). Every quote version carries `FOREIGN KEY (quote_id, user_id) REFERENCES ledger_quote_lineages(quote_id, user_id)`, so one `quote_id` can never hold versions belonging to two users; `issueQuote` on an existing `quote_id` collides on the lineage `PRIMARY KEY` and is rejected `QUOTE_STALE` for the quote's own owner and a foreign caller alike (no probing).
- **"Latest version" is derived**, never stored: `max(version_no)` for the `quote_id`, read under the wallet lock (or, for `assessQuoteForAuthorization`, read without a lock since the function is read-only — see the honest limit below). "Lineage authorized" will be derived in S5 from `ledger_authorizations UNIQUE(quote_id)`; S3 implements neither that check nor `renewQuote`'s refusal of an already-authorized lineage — both arrive in S5, and this is not stubbed here.
- `issueQuote` / `renewQuote` are **system-actor** commands (`actor: "system", component: "quotes"`, `expectedUserId` = the quote owner; `commandKind` `"quote_issue"` / `"quote_renew"`). The priced values (`maxHoldUnits`, `creditsQuoted`, allocations) come from the caller's pricing service, never from a customer request body; the repo ships **no `PricePolicyPort` implementation**. `ensureWallet(db, userId)` runs before the command because `runLedgerCommand`'s wallet lock requires the row to exist; creating the empty wallet is not itself a balance change (D3).
- **The ledger computes `content_sha256` itself**: SHA-256 of canonical JSON `{ quoteView, modelRef, allocations }` (allocations ordered by `operationIndex`) via `ledger-core.ts`'s existing `canonicalRequestHash`; a caller-supplied hash is never accepted (D10). `quote_view` is an **issue-time snapshot**: its embedded `wallet` summary and `authorizationHint` are display data that go stale the moment the wallet or lineage changes; nothing in S3 or later authorizes from them — `assessQuoteForAuthorization` re-derives staleness, expiry and price-version freshness from the row's own columns and from the injected ports, never from the snapshot's `wallet`/`authorizationHint` fields.
- **Trust note.** Quotes are server-created, immutable and hash-bound; they cannot mint credit (no entry, no wallet-table write anywhere in `ledger-quotes.ts` — the static scans below prove it). A forged or tampered quote could only change what a customer is asked to consent to, which is why quote creation stays a system-actor path (never a customer-supplied shape) and the runtime role's privileges on the three tables are `SELECT, INSERT` only (no `UPDATE`), proven as a restricted non-superuser role in `ledger-privileges.test.ts`.
- **Code-before-SQL validation, with the DB as backstop, not the first line.** `issueQuote`/`renewQuote` parse the view (`QuoteViewV3Schema`) and the allocation shapes before opening the command; the *business* check — for `final_*` quotes the caller's `modelRef` must equal `view.modelQualificationSnapshotId`; allocations must be contiguous from 0 and sum exactly to `view.maxHoldUnits` / `view.creditsQuoted`; promo quotes carry none — runs **inside** the `runLedgerCommand` callback, after the wallet lock (and, for `renewQuote`, after the CAS check below). This is deliberate: a `LedgerBusinessRejection("ALLOCATION_INVALID")` thrown there is persisted under the idempotency key by `runLedgerCommand`'s existing savepoint mechanism (S2) and replays identically without re-running the callback — verified by test ("a persisted ALLOCATION_INVALID rejection replays identically...").

**A1 — renewQuote is compare-and-swap (root-approved addendum).** `RenewQuoteInput` carries `expectedLatestVersionNo` (integer ≥ 1): the latest version the caller observed. Under the wallet lock, the store re-reads `max(version_no)` for the `quote_id`; if it does not equal `expectedLatestVersionNo`, the command throws `LedgerBusinessRejection("QUOTE_STALE")` (persisted, replays identically). An absent or foreign lineage is the same `NOT_FOUND` either way.

**A2 — fail-safe if the wallet lock is ever bypassed (executed).** Two raw connections (the superuser test fixture, no `runLedgerCommand`, no wallet lock) racing to `INSERT` version `k+1` directly into `ledger_quotes`: exactly one succeeds; the other fails `23505` (the `UNIQUE(quote_id, version_no)` backstop) or `23000` (the contiguity trigger) — never a duplicate, never a gap. Test: `ledger-concurrency.test.ts` "A2 fail-safe...". The design never rests on the lock alone.

**A3 — concurrency tests (`ledger-concurrency.test.ts`, extends the one 100-way file per D15).**
- (a) 100 concurrent `renewQuote` calls, distinct idempotency keys, all naming the same `expectedLatestVersionNo` → exactly one succeeds (version `k+1`); the other 99 get `QUOTE_STALE`; the table gains exactly one row.
- (b) 100 concurrent `renewQuote` calls with the *same* key (and payload) → exactly one new version; every caller observes the identical result (replayed via S2's idempotency machinery).
- (c) a sequential chain, each call naming the version it just received, produces contiguous versions.
- (d) after (a), `assessQuoteForAuthorization` on the superseded version `k` reports `QUOTE_STALE` — a superseded version can never be the target of an authorization.

**A4 — binding invariant (BINDING for every future M7 step, S5/S6 included): every ledger command takes the user's wallet row `FOR UPDATE` first.**
1. `ledger-isolation.test.ts` ("A4(1)") runs each command kind implemented in `src` today (`grant_credits`, `quote_issue`, `quote_renew`) against a spying connection (a `LedgerDb` test double exposing both `query` for `ensureWallet` and `acquire` for `runLedgerCommand`) and asserts the first statement touching a ledger table **after `BEGIN`** is `SELECT 1 FROM vynvori_ledger.wallets WHERE user_id = $1 FOR UPDATE` — scoped to after `BEGIN` because `ensureWallet`'s own upsert is a separate pre-transaction statement, not part of the command's own invariant.
2. `ledger-isolation.test.ts` ("A4(2)") statically scans every file under `packages/db/src` for a `commandKind:` string literal and fails if any is not in the registered list `["grant_credits", "quote_issue", "quote_renew"]` — S5/S6 must register their kinds here, and will fail this test if they skip the wallet lock.
3. `ledger-isolation.test.ts` ("A4(3)") statically asserts that `INSERT INTO` statements for `ledger_quotes`, `ledger_quote_allocations` and `ledger_quote_lineages` appear only in `ledger-quotes.ts`.

**A5 — honest limit (stated, not overclaimed).** The runtime role runs everything through `runLedgerCommand`, so by *design* it keeps `SELECT, INSERT` on the three quote tables. A code path that wrote quote rows **outside** `runLedgerCommand` is therefore not impossible by privilege alone — the database constraints (`UNIQUE(quote_id, version_no)`, the contiguity trigger, the composite lineage FK, the deferred sum triggers) are what make such a path fail-safe (A2 proves this empirically). A definer-only write path is the same architecture question as the grant-source HARD GATE (M4/W3) and is out of scope for S3. **The S9 runtime grants for S3 are exactly:** `SELECT, INSERT` on `ledger_quote_lineages`, `ledger_quotes`, `ledger_quote_allocations`; **no `UPDATE`** on any of the three; **no `EXECUTE`** on either new function (`ledger_quotes_check_version()`, `ledger_quote_check_allocation_sums()`); nothing granted in the migration itself (verified: `0003_quotes.sql` contains no `GRANT`).

**A6.** `docs/implementation/M7-Plan.md` is not edited by this step; the manager's docs-only plan-text update (D7/D10, §14) is tracked separately and, per the brief, this ADR addendum's Design section is the binding text if that PR has not yet merged.
