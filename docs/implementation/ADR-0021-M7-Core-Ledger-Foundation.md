# ADR-0021 — M7 credit-ledger core: foundation (S1)

Status: **proposed, implemented locally for S1 only; not deployed.** Base commit `1fa10e8551211a3ad8611074634773a3f5125b34`. Branch `claude/youthful-johnson-p85ycz`. Plan: `docs/implementation/M7-Plan.md` (rev 4), step S1. Founder approved S1 on 2026-11-02 (direct instruction in session). This ADR records the plan's design decisions as the contract that S2–S9 implement; S1 itself ships **no tables, no wallet or quote logic, no workflows and no dependencies**.

## Context
M7 needs a Neon/Drizzle credit ledger (whole-number credits; `available` / `reserved` / `held_for_review` buckets; append-only entries; versioned quotes; reserve → settle/release; reconciliation hold on unknown provider outcome). Medusa stays the system of record for commerce and is never written from Drizzle. Every financial/paid flag stays OFF; no price, credit cost, package size, hold duration or cut-off may be invented. S1 lays the verified foundation: this ADR, a hash-pinned migration journal with a tested rollback, additive server-only contracts, and the per-file Postgres test harness.

## Decisions (D1–D15; final wording is the plan's §5, which S2–S9 implement)
- **D1 Actor key.** `wallets.user_id uuid PRIMARY KEY REFERENCES vynvori_identity.profiles(id) ON DELETE RESTRICT`; every owned row carries `user_id`. No guest wallets, no email column, no Medusa customer id.
- **D2 Buckets and balanced entries.** `available/reserved/held_for_review/consumed` as `bigint CHECK (>= 0 AND <= 9007199254740991)`; every entry has five deltas summing to zero with a per-`entry_kind` sign pattern (`grant`, `reserve`, `release`, `settle`, `hold`). `0 < charge ≤ hold`. Hold-resolution kinds and anything entering or leaving `operator_remedy` are deferred to the remedy milestone.
- **D3 Database-enforced immutability.** `ledger_entries` append-only (triggers); wallet and reservation state change only through the entry trigger (guard: `pg_trigger_depth() > 1` AND current user = owner of the `SECURITY DEFINER` apply function — see the S2 addendum; the depth check alone is bypassable); unique cause `(cause_kind, cause_ref)`; one of release/settle/hold per reservation. **Binding for S5:** the reservation-state guard (and every other guard protecting state that a trigger writes) must use the same pattern as the wallet guard — a `SECURITY DEFINER` writer function, a guard that requires `current_user` to be the *owner of that writer function* (compared by name via `pg_get_userbyid`, never a `regrole` cast), `pg_trigger_depth() > 1`, and a trigger-context check (`TG_RELID`, `TG_OP`, `TG_WHEN`, `TG_LEVEL`) in every trigger function. `pg_trigger_depth()` alone is never a sufficient guard: executed bypass — a trigger on a role-owned `TEMP` table fires at depth 1, so its nested `UPDATE` sees depth 2.
- **D4 Idempotency.** Immutable `ledger_commands`; `UNIQUE(scope, idempotency_key)`, `scope = {user_id}:{command_kind}`; same key + same hash replays, different hash is `IDEMPOTENCY_CONFLICT`; terminal business rejections are persisted under the key, transient failures are not. The contract envelope (S1) encodes the scope rule and key format.
- **D5 One reservation per provider operation**, bundle allocations frozen in the quote; the ledger verifies and never computes a split or rounding remainder.
- **D6 Release, settle and hold are evidence-gated and never auto-resolved.** Settle needs `persisted_delivered` with verified manifest and owner/rights; release needs `verified_zero_charge_failure` only (no pre-dispatch release — founder question Q9); hold needs `outcome_unknown` or `persistence_failed_under_review`. A vendor-charge message is never evidence. No timer or sweeper.
  **S5/S6 GATE (carry-forward):** the evidence in S1 is caller-asserted and forgeable (`hasVerifiedManifestHash: true` and `ownerAndRightsVerified: true` are literals a caller can type). S5/S6 must replace the booleans with values the ledger compares to persisted rows (`manifestSha256` against the stored manifest, `reservationId`, owner read from the database) and accept evidence only from `system` actors through `LedgerInternalCommandV1Schema`. Parse success is never authorization.
- **D7 Quotes.** Immutable `ledger_quotes` with `UNIQUE(quote_id, version_no)`, a locked lineage pointer, authorization checks in one transaction ending in a default-deny `AuthorizationEligibilityPort`. Column ↔ contract mapping:

  | Column | Contract field |
  |---|---|
  | `max_charge_units` | `maxHoldUnits` |
  | `credits_quoted` | `creditsQuoted` |
  | `price_version` | `pricePolicyVersion` |
  | `operation_kind` | `offerKind` |
  | `model_ref` | `modelQualificationSnapshotId` for finals; for bundles the concept-model snapshot reference **supplied by the issuer** (the bundle contract has no model field — additive note for S3) |

  `LedgerQuoteRecordV1` uses the column-side names and stores the validated `QuoteViewV3` separately.
- **D8 Promo uniqueness** per verified `issuer + subject`; entitlement, not a wallet debit; evidence-gated events.
- **D9 Packages and refinement slots** (scaffolding), including the C-02 reopen rule via root's guard.
- **D10 Locking and outcomes.** Lock order: lineage → wallet → reservations by `id`; transaction-scoped features only (Neon pooled connections); `LEDGER_OUTCOME_UNKNOWN` is resolved by replaying the same key.
  **Outcome classification — the binding rule (S2 wording).** *Before `COMMIT` is sent:* an error that carries a SQLSTATE **and** severity `ERROR` is a **definite** rollback in every SQLSTATE class (including 57014 statement timeout/cancel and any server-reported 08xxx `ERROR`); an error with no SQLSTATE or no severity, any `FATAL`, and the driver's own client-level failures ("not queryable", "Client was closed", "Connection terminated") are `LEDGER_OUTCOME_UNKNOWN`, in every phase, because the client cannot know what the server did. *While `COMMIT` is in flight:* definite only for severity `ERROR` in SQLSTATE classes 23 and 40 (one deliberate tightening: 40003 `statement_completion_unknown` is by definition unknown and is never definite); everything else is `LEDGER_OUTCOME_UNKNOWN`. The classifiers are pure, exported and tested per branch. They rely on the server's English severity string: an unrecognised locale degrades to `LEDGER_OUTCOME_UNKNOWN`, never to a wrong "definite".
  **Two different kinds of "unknown".** A `COMMIT`-time failure is a *database-transaction* failure whose true state is unknown to the caller; it is resolved by replaying the same idempotency key. That is different from a *provider-outcome* "unknown", which creates a reconciliation hold, is never auto-resolved and never retried.
  **Further carry-forwards:** the ledger must compute `contentSha256` / `requestSha256` itself and never trust a caller-supplied value; a zero-credit quote is legal only for the promo kind (no allocations) and S3 must enforce `max_charge_units > 0` for every other kind; an `EligibilityDecisionV1` is bound to a single inline call and must never be cached.
- **D11 Ownership.** Every predicate carries `user_id`; absent and foreign ids return the same `NOT_FOUND`; internal transitions carry `actor` + `expectedUserId`.
- **D12 Funding in W1: a grant-source registry, not a flag.** `0002` registers no sources; the runtime role gets no `INSERT` on the registry, so runtime privileges alone cannot mint credits.
- **D13 Not reachable from runtime.** Static test from S2: nothing under `apps/` and no non-test module imports `@vynvori/db/ledger*`; no numeric constants exported; flags all `false`. S1 satisfies this trivially (no ledger code is imported anywhere).
- **D14 Read-only checks** (`checkWalletInvariants`, `findOrphanedReservations` with a required cut-off, report-only).
- **D15 Test databases and connection budget** — recorded below.

## Connection budget (D15)
Each ledger test file owns database `vynvori_m7_<name>_test`; the fixture allow-list currently contains `migrations`, `fixture`, `concurrency`, `core`, `privileges` (later steps append). The single 100-way file `ledger-concurrency.test.ts` (from S2) may use up to **110** connections; every other ledger file caps its pool at **5** (≤ 9 files ⇒ ≤ **45**). Existing suites, counted at their declared maxima in the repository: `auth-state.test.ts` 6, `composition-pg.test.ts` 4, runtime pools in `packages/db/src/{index,identity}.ts` 3 + 3 = **16**. Pools alone give 110 + 45, but each DB-using file also holds one persistent client and one transient admin/probe connection, so the worst case is about **112** for the concurrency file plus **7** for each of the 9 other DB-using files (**63**) = about **175**, plus **16** for the existing suites = about **191**, below `250 − 3 reserved superuser slots = 247` (CI sets `max_connections=250` and asserts it in `.github/workflows/m2.yml`, root-owned). The fixture reads `SHOW max_connections`; `ledgerPool` clamps to `max_connections − 3` and reports `degraded` when the server limit is below the requested cap. It clamps a **single** pool and cannot see other files' usage; if the sum ever approaches the limit, root may serialize the Postgres suites with `--test-concurrency=1`. From S2 the concurrency file must **fail** under `CI_REQUIRE_PG_TESTS=1` when degraded; locally it runs reduced and its 100-connection row is `NOT_RUN`. Measured in CI by S9, not by S1.

## Test harness semantics
Postgres-backed tests gate on `M7_TEST_POSTGRES_URL` or `M2_CREATIVE_DATABASE_URL`. URL present ⇒ run. Absent and `CI_REQUIRE_PG_TESTS=1` ⇒ the test **fails**. Absent otherwise ⇒ skipped, reported `NOT_RUN`, never PASS. `CI_REQUIRE_PG_TESTS` is deliberately not a `VYNVORI_*` variable (`packages/shared` rejects unknown `VYNVORI_*` keys). The fixture refuses any target that is not `127.0.0.1` + user `synthetic` + an **explicit port** (only `5432`, CI's value, unless `M7_TEST_POSTGRES_PORT_ACK` names exactly the port used by a local throwaway server) + no query string or fragment + an allow-listed `vynvori_m7_<name>_test` database. On the maintenance connection, **before any `DROP`/`CREATE DATABASE`**, the fixture asserts server-side that `current_user = 'synthetic'` **and** `current_setting('is_superuser') = 'on'` (CI's `synthetic` is the bootstrap superuser — the `foundation` job already runs `ALTER SYSTEM SET max_connections` as it — whereas managed databases normally give application roles no superuser); it is exercised by the CI Postgres test and unit-tested for wrong user and non-superuser. The server **address is deliberately not checked**: an earlier revision asserted `inet_server_addr()` is loopback, which failed in CI because the Postgres service is a Docker container reached through a published port, so the server sees the container-side address rather than `127.0.0.1`. **Residual risk:** a loopback SSH tunnel to a remote server on which `synthetic` is a superuser still passes these checks; the blast radius is confined to the allow-listed database names (and the auth DDL applied inside them).

### Security-review dispositions (S1)
Fixed in S1: fixture target guard now rejects any URL query/fragment (pg lets `?host=`/`?user=` override the authority) and never echoes a malformed URL; the down script's guard and drops are one atomic statement (safe under plain `psql -f`); user ids must be lowercase UUIDs so case variants cannot fork idempotency scopes; quote `expiresAt` must follow `issuedAt`. Carried forward: settle/release/hold evidence parse success is **not** authorization — S5/S6 must bind it to persisted state read by the ledger and restrict it to `system` actors (S6 gate); `FORBIDDEN_PUBLIC_FIELDS` now also lists `requestSha256`, `evidenceRef`, `modelRef` and `contentSha256` (root-granted additive edit, none is used in a public shape on `main`). `capabilitySnapshotId` is deliberately **not** listed: it is a public field (`quote.ts`, `studio-plan.ts`), and it stays out of customer projections only because `ledger-internal.ts` is `server-only` and absent from the public barrel (tested). Concurrent runs of the same test name on a shared server would drop each other's database (CI uses a private server per job).

## Rollback
- Code: revert the PR; the ledger is unreachable from runtime.
- Data: `rollback/0001_ledger_schema.down.sql` (manual; guarded). It refuses while any relation exists in `vynvori_ledger`, drops `vynvori_ledger`, then drops the journal schema `vynvori_ledger_migrations` so up → down → up does not trip the drift check. Rollbacks apply in reverse numeric order. **Caveat (not hidden):** once later migrations add append-only tables, deleting rows needs a superuser to disable triggers; removing real ledger data is **restore from backup**, not "run the down script".
- **Half state (manual path):** if the journal schema `vynvori_ledger_migrations` exists but `vynvori_ledger` does not (an interrupted manual run), the down script reports `schema not present` and the runner reports `HISTORY_OR_SCHEMA_DRIFT`. An operator confirms with `SELECT current_database()` that the target is disposable or backed up, checks `\dn vynvori_ledger*`, and runs `DROP SCHEMA vynvori_ledger_migrations CASCADE;` by hand (nothing else lives in it), then re-applies. The down script takes the runner's advisory lock `(742110, 7)`, sets `lock_timeout`, and schema-qualifies its catalog references.
- Tested: up → down → up, rollback refusal while a relation exists, and half-state drift detection in `ledger-migrations.test.ts`.

## S2 addendum — wallet, immutable command log, append-only ledger (migration `0002_wallet_ledger`)
Status: **proposed, implemented locally for S2 only; not deployed.** Plan step: `M7-Plan.md` §7 S2. Nothing in S2 adds a flag, a dependency, a route or a runtime import (static test `ledger-isolation.test.ts`, D13).

**What S2 adds.** Tables `wallets`, `ledger_commands`, `ledger_grant_sources`, `ledger_entries` in `vynvori_ledger`; `packages/db/src/ledger-core.ts` (`ensureWallet`, `getWalletSummary`, `canonicalRequestHash`, `runLedgerCommand`, `appendGrantEntry`, the pure classifiers); the `./ledger-core` export. `0002` inserts **no rows**: no grant source is registered, so after the migration no credit can be created by anyone. No exported function registers a source; the test fixture does it as the superuser and lives in `tests/` only.

**Outcome classification as implemented (D10).** Exactly the binding rule in D10 above. Mapping of definite server errors: class 23 → `DATABASE_REJECTED`; 40001/40P01/55P03/57014 → `TRANSIENT`; otherwise `DATABASE_ERROR`; none records anything under the key. Every statement runs on a connection wrapper that tags driver-originated errors, so a *callback's own bug* (a `TypeError`, a thrown `null`) is a generic `DATABASE_ERROR` without its message, not a database outcome. A connection that produced an unknown outcome is destroyed, never returned to the pool; a pooled client has an `error` listener for as long as it is checked out (otherwise a connection that ends between statements would be an unhandled `error` event that crashes the process). This is a database-transaction uncertainty; it is not a provider-outcome unknown and creates no reconciliation hold.

**Idempotency as implemented (D4).** The ledger computes `requestSha256` itself from sorted-key canonical JSON of the payload (non-finite numbers, unsafe integers, `undefined`, bigint and class instances are rejected). The wallet row is locked `FOR UPDATE` first, so same-user commands serialize there; the command row is then inserted `ON CONFLICT (scope, idempotency_key) DO NOTHING`. Existing row + same hash replays the result reconstructed from `ledger_entries`; different hash is `IDEMPOTENCY_CONFLICT`; the callback never re-runs. `LedgerBusinessRejection` is persisted as a `rejected` command row **in the same transaction under a savepoint while the wallet lock is held** (see *Command-transaction guarantees*; only the codes in `PERSISTABLE_REJECTION_CODES`), replays identically and cannot succeed after a later top-up. `source_ref` uniqueness (`UNIQUE (cause_kind, cause_ref)`) makes a second grant under a *new* key a `DUPLICATE_CAUSE`, not a second grant. Idempotency keys and hashes are never placed in error messages.

**Privilege model B as implemented — binding.** The migration contains **exactly one `SECURITY DEFINER` function**, `ledger_entries_apply_to_wallet()` (the only writer of wallet balances); every other function (`reject_mutation()`, `wallets_insert_guard()`, `wallets_update_guard()`, `ledger_entries_check_command()`) is invoker-rights. Every function pins `SET search_path = pg_catalog, pg_temp` (`pg_temp` last; `vynvori_ledger` is deliberately not in the path; bodies are fully schema-qualified, no dynamic SQL) and gets `REVOKE ALL ON FUNCTION … FROM PUBLIC` — the only `REVOKE` a migration may contain; the migration grants nothing and names no runtime role. `wallets_update_guard` rejects unless **both** `pg_trigger_depth() > 1` **and** `current_user` is the **owner of `ledger_entries_apply_to_wallet()`** (compared by name with `pg_get_userbyid`, null-safe via `IS DISTINCT FROM`; never through a `regrole` cast, which case-folds and parses identifiers). **The real invariant: the guard's only legitimate writer is the owner of the apply function.** The rollout re-owns only the function, so the guard must follow the function, not the table. Under the definer path `current_user` is that owner; a trigger created by any other role runs as that role and is rejected even if the role holds broad write rights such as `pg_write_all_data`. **Direct invocation of the definer function by the runtime role fails both without `EXECUTE` (42501) and with it (0A000, "trigger functions can only be called as triggers"; tested).** **Every trigger function also verifies what fired it** and raises otherwise: the four table-bound functions (`wallets_insert_guard()`, `wallets_update_guard()`, `ledger_entries_check_command()`, `ledger_entries_apply_to_wallet()`) pin `TG_RELID` (by `regclass`), `TG_OP`, `TG_WHEN` and `TG_LEVEL`; `reject_mutation()` is shared by all append-only tables and therefore pins the schema (`TG_TABLE_SCHEMA`), timing, operation and level instead (it can only raise, so it is harmless on any table). So a role that is ever given `EXECUTE` on the definer function cannot attach it to a trigger on its own `TEMP` table and mint credits. *Test coverage:* the `TG_RELID` branch of the apply function is behaviour-tested (`EXECUTE` granted, `TEMP` table); the `TG_OP`/`TG_WHEN`/`TG_LEVEL` branches and the other four functions are covered statically only, and S9 adds behaviour tests for them (hardening, not an escalation risk).

**Evidence from the S2 security review (executed on PostgreSQL 16, independently reproduced).** Three holes were found and fixed: (1) *guard bypass by a TEMP trigger* — a role with exactly model A's grants plus the default `TEMP` privilege created a trigger on its own temp table whose function (in `pg_temp`) updated `wallets`; it fires at depth 1, so the wallet guard saw depth 2 and passed (`available_units` became 1000000 with `revision = 0` and zero entries); the depth guard cannot tell the ledger-entry trigger from any other trigger → fixed by the definer function (the runtime role needs no balance `UPDATE`) and the owner check. (2) *`FOR UPDATE` needs `UPDATE` privilege* (42501 without it) → the runtime role needs **column-level `UPDATE (user_id)` on `wallets` only**; a no-op `SET user_id = user_id` fires the guard and is rejected, so no balance can change; `lockWallet` keeps `SELECT … FOR UPDATE`. (3) *broad write roles defeat a depth-only guard* (`pg_write_all_data`, which a managed-database admin role may include) → the owner check. `ledger-privileges.test.ts` proves all of this as non-superuser roles (CI's `synthetic` is a superuser and would pass any design) and the mutation table below shows which named test fails for each deliberate weakening.

**Binding consequences.**
- **The definer's effective privilege equals the owner's.** The existing staging migration owner is known to be over-privileged (CREATEDB, CREATEROLE, BYPASSRLS; see `M2-Creative-Staging-Plan-20261018.md`). **Rollout stays unauthorized until a dedicated `NOLOGIN`, `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEROLE` role owns the functions (`ALTER FUNCTION … OWNER TO …`), delivered inside the S9 grants proposal for the founder to execute. This is a precondition, not an option.**
- **The S9 grants proposal must include:** a dedicated `NOLOGIN`, `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEROLE` definer owner role; `ALTER FUNCTION vynvori_ledger.ledger_entries_apply_to_wallet() OWNER TO` it; to that role **exactly** `USAGE` on schema `vynvori_ledger` and `SELECT` and `UPDATE` on `vynvori_ledger.wallets` — nothing more (no INSERT, DELETE, TRUNCATE, REFERENCES or TRIGGER), and nothing else the function body touches, because the function touches nothing else. The list is derived from the code by test, not from memory: `ledger-privileges.test.ts` gives a dedicated owner only these three privileges, shows the legitimate `runLedgerCommand` + `appendGrantEntry` path works, then shows it fails with `42501` when any one of the three is removed (so the list is neither missing something nor padded). These grants are executed by the founder in S9, never by a migration; runtime column-level `UPDATE (user_id)` on `wallets` only; `REVOKE TEMPORARY ON DATABASE … FROM PUBLIC` for the ledger database (revoking from the role alone does nothing while `PUBLIC` holds it); **`EXECUTE` on the definer functions is NOT granted to the runtime role, and never through a blanket schema-wide `GRANT EXECUTE ON ALL FUNCTIONS`**; a runtime role that is not the table owner (a runtime role that owns the tables can `DISABLE TRIGGER` and bypass everything, so the owner must be distinct), not a member of `pg_write_all_data` or any managed-database superuser-like role; owner distinct from runtime; and the HARD GATE text below.
- **BINDING S9 precondition — the definer owner has no members and the runtime role cannot `SET ROLE` to it (executed exploit path).** After the re-own step, no role other than the definer itself may be a member of (or able to `SET ROLE` to) the definer owner role: not the runtime role, not the migration login. Executed on PostgreSQL 16: `GRANT <definer> TO <runtime>`, then as runtime `SET ROLE <definer>` and a `TEMP`-table trigger issuing `UPDATE wallets` passes the guard (`current_user` is the function owner, depth 2) and minted — the wallet reached 777 with no ledger entry. S9 must assert this by test after the re-own step (`pg_has_role(<runtime>, <definer>, 'member') = false`, `pg_has_role(<runtime>, <definer>, 'usage') = false`, also for a runtime variant that holds `pg_write_all_data`), and `ledger-privileges.test.ts`'s structural assertion today only covers the pre-re-own table owner.
- **BINDING S9 owner-change procedure (must be executable by the role that will run it).** `ALTER FUNCTION … OWNER TO <definer>` requires the executing role to be a superuser, or to be able to `SET ROLE` to the new owner **and** the new owner to hold `CREATE` on schema `vynvori_ledger` at that moment. On a managed database the executor is not a true superuser, so the procedure is: (1) transiently `GRANT <definer> TO <executor>` and `GRANT CREATE ON SCHEMA vynvori_ledger TO <definer>`; (2) `ALTER FUNCTION vynvori_ledger.ledger_entries_apply_to_wallet() OWNER TO <definer>`; (3) **immediately** `REVOKE <definer> FROM <executor>` and `REVOKE CREATE ON SCHEMA vynvori_ledger FROM <definer>`; (4) assert the end state: the definer holds exactly `USAGE` on the schema plus `SELECT` and `UPDATE` on `wallets`, `has_schema_privilege(<definer>, 'vynvori_ledger', 'CREATE') = false`, and it has no members. The privilege test performs the re-own as the superuser fixture, which hides step 1; S9 adds a test that runs the procedure as a non-superuser executor and asserts the end state. The "exactly" claim is a *minimal necessary* set (each of the three is necessary — removing any one gives `42501`); it does not prove that nothing extra is harmless (e.g. an extra `INSERT` still works; column-level `UPDATE` on the five bucket columns also suffices), so S9 keeps the list as written and treats any additional privilege as a deviation to be justified.
- **HARD GATE.** "No real grant source may be registered by any means (migration, seed, runtime, operator script) before grant writes sit behind a definer command function bound to verified external evidence. Gate for M4 and W3; precondition in the S9 grants proposal." Reason: the runtime role needs `INSERT` on `ledger_entries` and `ledger_commands`, so once any grant source is registered it can mint up to the entry bounds. In W1 no source exists and the runtime cannot create one (no `INSERT` on `ledger_grant_sources`, asserted as a restricted role).


**Other S2 review dispositions.** Fixed (rounds 1–2): rollback now takes `ACCESS EXCLUSIVE` locks on the four tables before the emptiness check (a writer committing between check and `DROP` would otherwise be destroyed silently), pins `search_path` and schema-qualifies catalogs; SQLSTATE `40003` (statement_completion_unknown) is an *unknown* outcome, only `40001`/`40002`/`40P01` and class 23 are definite; `LedgerDb` no longer accepts a bare `Client` (cannot be destroyed, interleaves transactions); the callback's `tx` handle is dead after the command ends; a broken connection after a failed `ROLLBACK` surfaces the original rejection and records nothing; `LedgerError` keeps only `{code, sqlstate, constraint}` (never the raw driver error, which can contain the idempotency key); `mapDefinite` guards non-object throws and never keeps the driver error; cyclic/deep payloads are `INVALID_INPUT`; test pools are created inside `try`; the termination test polls `pg_stat_activity`; an export allow-list test makes any new `ledger-core` export (e.g. another minting path) a deliberate change. Tracked, not fixed here: an entry may reference an earlier-committed applied command (S5's binding trigger must require the same transaction); `ENABLE ALWAYS TRIGGER` against `session_replication_role=replica` (superuser-only, outside the runtime role); `severity` is localised, so CI/fixtures must run an English `lc_messages` (fails safe to unknown); replay order within one command uses `created_at, entry_id` and needs a sequence once a command can write several entries; sums of the four buckets can exceed 2^53-1, so JS must never add buckets.

**Command-transaction guarantees (round 2).** A terminal business rejection is recorded **in the same transaction** under a `SAVEPOINT` while the wallet lock is held (`ROLLBACK TO SAVEPOINT`, insert the `rejected` row, `COMMIT`), so no top-up can slip between the decision and its record; *once a key is recorded, its callback never runs again* (two concurrent same-key commands whose callback rejects run it exactly once). After `BEGIN` every command sets `lock_timeout` (10 s), `statement_timeout` (30 s) and `idle_in_transaction_session_timeout` (30 s) — private technical bounds, not business values (the S1 runner uses `lock_timeout` 4 s); `options.lockTimeoutMs` can only shorten the lock wait. A stalled lock holder makes a waiter fail with `TRANSIENT` (55P03) and release its connection. The idempotency hash binds the **actor kind** plus the payload, and `appendGrantEntry` requires the command's hash to equal the hash of the very entry it writes (actor, source, ref, amount), so an empty or different caller payload cannot record one effect under a key and write another; a hand-built or copied transaction handle is rejected (handles are issued only by `runLedgerCommand`, tracked in a module-private `WeakSet`); the handle is dead after the command ends. Canonicalisation has a node budget and ancestor tracking (cycles and shared deep structures are `INVALID_INPUT`); huge or sparse arrays are rejected by length before iterating. Connection acquisition is inside the error boundary (a failing `connect()` becomes a bare `TRANSIENT` `LedgerError`, never the driver error with host/port), pools are recognised by a `connect` function rather than `instanceof` (a second `pg` copy or a serverless pool works), and the issued transaction handle is frozen.

**Break-glass — operational note, not a code bypass.** After the function is re-owned to the dedicated role, a *superuser that is not the function owner* is blocked by the guard too: it cannot `UPDATE wallets` directly or through a trigger. There is no bypass in the code and none is added. **Re-owning the function back does not by itself permit a correcting `UPDATE`:** the guard also requires `pg_trigger_depth() > 1`, so even the function owner cannot `UPDATE wallets` directly (reproduced). The audited break-glass options are (a) restore from backup, or (b) `ALTER TABLE vynvori_ledger.wallets DISABLE TRIGGER wallets_update_guard` by the table owner or a superuser in a reviewed, time-boxed, audited step, then re-enable it — never a silent `UPDATE`. A table owner that is also the runtime role can do (b) at will, which is why the owner must be distinct from the runtime role.

## S3 addendum — versioned quotes, insert-only lineage anchor, frozen allocations (migration `0003_quotes`)
Status: **proposed, implemented locally for S3 only; not deployed.** Plan step: `M7-Plan.md` §7 S3. Nothing in S3 adds a flag, a dependency, a route or a runtime import (D13, extended below). `0003_quotes.sql` adds no `GRANT`, no `CREATE`/`ALTER ROLE`, no `OWNER TO`; the only `REVOKE` is function-level `FROM PUBLIC`; it adds **no** `SECURITY DEFINER` function — the migration set still keeps exactly one (S2's `ledger_entries_apply_to_wallet()`).

**Design (binding for S3; refines plan D7/D10).**
- Every quote operation (`issueQuote`, `renewQuote`) is a ledger **COMMAND of the quote owner run through `runLedgerCommand`**, which locks the user's wallet row `FOR UPDATE` first (ADR-0021 D10). All of one user's quote operations therefore serialize on that wallet lock. There is **no lineage lock and no mutable lineage pointer**: this replaces plan D10's "lineage" lock step and D7's "mutable pointer table" with the lock order wallet → (later, S5) reservations by id.
- `ledger_quote_lineages` is an **insert-only anchor**: `(quote_id text PRIMARY KEY, user_id uuid NOT NULL REFERENCES vynvori_identity.profiles(id) ON DELETE RESTRICT, created_at, UNIQUE (quote_id, user_id))`, immutable (`UPDATE`/`DELETE`/`TRUNCATE` rejected via `reject_mutation()`, reused from S2 — no new immutability function was needed). Every quote version carries `FOREIGN KEY (quote_id, user_id) REFERENCES ledger_quote_lineages(quote_id, user_id)`, so one `quote_id` can never hold versions belonging to two users; `issueQuote` on an existing `quote_id` collides on the lineage `PRIMARY KEY` and is rejected `QUOTE_STALE` for the quote's own owner and a foreign caller alike (no probing).
- **"Latest version" is derived**, never stored: `max(version_no)` for the `quote_id`, read under the wallet lock (or, for `assessQuoteForAuthorization`, read without a lock since the function is read-only — see the honest limit below). "Lineage authorized" will be derived in S5 from `ledger_authorizations UNIQUE(quote_id)`; S3 implements neither that check nor `renewQuote`'s refusal of an already-authorized lineage — both arrive in S5, and this is not stubbed here.
- `issueQuote` / `renewQuote` are **system-actor** commands (`actor: "system", component: "quotes"`, `expectedUserId` = the quote owner; `commandKind` `"quote_issue"` / `"quote_renew"`). The priced values (`maxHoldUnits`, `creditsQuoted`, allocations) come from the caller's pricing service, never from a customer request body; the repo ships **no `PricePolicyPort` implementation**. `ensureWallet(db, userId)` runs before the command because `runLedgerCommand`'s wallet lock requires the row to exist; creating the empty wallet is not itself a balance change (D3).
- **The ledger computes `content_sha256` itself**: SHA-256 of canonical JSON `{ quoteView, modelRef, allocations }` (allocations ordered by `operationIndex`) via `ledger-core.ts`'s existing `canonicalRequestHash`; a caller-supplied hash is never accepted (D10). `quote_view` is an **issue-time snapshot**: its embedded `wallet` summary and `authorizationHint` are display data that go stale the moment the wallet or lineage changes; nothing in S3 or later authorizes from them — `assessQuoteForAuthorization` re-derives staleness, expiry and price-version freshness from the row's own columns and from the injected ports, never from the snapshot's `wallet`/`authorizationHint` fields.
- **Trust note.** Quotes are server-created, immutable and hash-bound; they cannot mint credit (no entry, no wallet-table write anywhere in `ledger-quotes.ts` — the static scans below prove it). A forged or tampered quote could only change what a customer is asked to consent to, which is why quote creation stays a system-actor path (never a customer-supplied shape) and the runtime role's privileges on the three tables are `SELECT, INSERT` only (no `UPDATE`), proven as a restricted non-superuser role in `ledger-privileges.test.ts`.
- **Code-before-SQL validation, with the DB as backstop, not the first line.** `issueQuote`/`renewQuote` parse the view (`QuoteViewV3Schema`) and the allocation shapes before opening the command; the *business* check — for `final_*` quotes the caller's `modelRef` must equal `view.modelQualificationSnapshotId`; allocations must be contiguous from 0 and sum exactly to `view.maxHoldUnits` / `view.creditsQuoted`; promo quotes carry none — runs **inside** the `runLedgerCommand` callback, after the wallet lock (and, for `renewQuote`, after the CAS check below). This is deliberate: a `LedgerBusinessRejection("ALLOCATION_INVALID")` thrown there is persisted under the idempotency key by `runLedgerCommand`'s existing savepoint mechanism (S2) and replays identically without re-running the callback — verified by test ("a persisted ALLOCATION_INVALID rejection replays identically...").

**A1 — renewQuote is compare-and-swap (root-approved addendum).** `RenewQuoteInput` carries `expectedLatestVersionNo` (integer ≥ 1): the latest version the caller observed. Under the wallet lock, the store re-reads `max(version_no)` for the `quote_id`; if it does not equal `expectedLatestVersionNo`, the command throws `LedgerBusinessRejection("QUOTE_STALE")` (persisted, replays identically). An absent or foreign lineage is the same `NOT_FOUND` either way.

**A2 — fail-safe if the wallet lock is ever bypassed (executed).** Two raw connections (the superuser test fixture, no `runLedgerCommand`, no wallet lock) racing to `INSERT` version `k+1` directly into `ledger_quotes`: exactly one succeeds; the other fails `23505` (the `UNIQUE(quote_id, version_no)` backstop) or `23000` (the contiguity trigger) — never a duplicate, never a gap. Test: `ledger-concurrency.test.ts` "A2 fail-safe...". The design never rests on the lock alone.

**A3 — concurrency tests (`ledger-concurrency.test.ts`, extends the one 100-way file per D15).**
- (a) 100 concurrent `renewQuote` calls, distinct idempotency keys, all naming the same `expectedLatestVersionNo` → exactly one succeeds (version `k+1`); the other 99 get `QUOTE_STALE`; the table gains exactly one row.
- (b) 100 concurrent `renewQuote` calls with the *same* key (and payload) → exactly one new version; every caller observes the identical result (replayed via S2's idempotency machinery).
- (c) a sequential chain, each call naming the version it just received, produces contiguous versions.
- (d) after (a), `assessQuoteForAuthorization` on the superseded version `k` reports `QUOTE_STALE` — a superseded version can never be the target of an authorization.

**A4 — binding invariant (BINDING for every future M7 step, S5/S6 included): every ledger command takes the user's wallet row `FOR UPDATE` first.**
1. `ledger-isolation.test.ts` ("A4(1)") runs each command kind implemented in `src` today (`grant_credits`, `quote_issue`, `quote_renew`) against a spying connection (a `LedgerDb` test double exposing both `query` for `ensureWallet` and `acquire` for `runLedgerCommand`) and asserts the first statement touching a ledger table **after `BEGIN`** is `SELECT 1 FROM vynvori_ledger.wallets WHERE user_id = $1 FOR UPDATE` — scoped to after `BEGIN` because `ensureWallet`'s own upsert is a separate pre-transaction statement, not part of the command's own invariant.
2. `ledger-isolation.test.ts` ("A4(2)") statically scans every file under `packages/db/src` for a `commandKind:` string literal and fails if any is not in the registered list `["grant_credits", "quote_issue", "quote_renew"]` — S5/S6 must register their kinds here, and will fail this test if they skip the wallet lock.
3. `ledger-isolation.test.ts` ("A4(3)") statically asserts that `INSERT INTO` statements for `ledger_quotes`, `ledger_quote_allocations` and `ledger_quote_lineages` appear only in `ledger-quotes.ts`.

**A5 — honest limit (stated, not overclaimed).** The runtime role runs everything through `runLedgerCommand`, so by *design* it keeps `SELECT, INSERT` on the three quote tables. A code path that wrote quote rows **outside** `runLedgerCommand` is therefore not impossible by privilege alone — the database constraints (`UNIQUE(quote_id, version_no)`, the contiguity trigger, the composite lineage FK, the deferred sum triggers) are what make such a path fail-safe (A2 proves this empirically). A definer-only write path is the same architecture question as the grant-source HARD GATE (M4/W3) and is out of scope for S3. **The S9 runtime grants for S3 are exactly:** `SELECT, INSERT` on `ledger_quote_lineages`, `ledger_quotes`, `ledger_quote_allocations`; **no `UPDATE`** on any of the three; **no `EXECUTE`** on either new function (`ledger_quotes_check_version()`, `ledger_quote_check_allocation_sums()`); nothing granted in the migration itself (verified: `0003_quotes.sql` contains no `GRANT`).

**A6.** `docs/implementation/M7-Plan.md` is not edited by this step; the manager's docs-only plan-text update (D7/D10, §14) is tracked separately and, per the brief, this ADR addendum's Design section is the binding text if that PR has not yet merged.

## S4 addendum — promo-claim uniqueness (migration `0004_promo_claims`)

**Scope.** One claim per verified identity (`issuer + subject`), recorded as an append-only event trail. Promo is an entitlement, not money: `ledger-promo.ts` contains no wallet or ledger SQL (asserted by a static test), and no real credit grant source is registered by any means. Hard gates are unchanged: the definer owner role and its grants stay founder-executed and are not in any migration; no `VYNVORI_*` flag is added or changed.

**Design.**
- `promo_claims`: `UNIQUE (issuer, subject)` (`promo_claims_identity_unique`), `UNIQUE (user_id)`, `UNIQUE (operation_id)` (`promo_claims_operation_unique`), composite FK `(issuer, subject)` → `vynvori_identity.profiles(issuer, subject)` (`promo_claims_profile_identity_fk`, `ON DELETE RESTRICT`), `CHECK ((state = 'eligible') = (event_seq = 0))`. A guest with no profile cannot claim.
- `promo_claim_events`: append-only; one row per state change, `UNIQUE (claim_id, seq)`, `UNIQUE (claim_id, from_state)`, `UNIQUE (command_id)`, composite FKs to the claim and to an applied `ledger_commands (command_id, user_id)` of the same user.
- The state graph is `PLANE_C_PROMO_GRAPH` from `state-machines.ts` (imported, not edited). SQL function `promo_claim_edge_allowed` mirrors the six legal edges and is tested against all 25 (from, to) pairs.
- **Evidence matrix** (CHECK on `(from_state, to_state, evidence_kind)`): `claim_unknown` resolves only through reconciliation kinds (`reconciled_delivered` → `consumed`, `reconciled_uncharged_failure` → `verified_uncharged_failure`); first-hand kinds cannot resolve it. `consumed` additionally requires verified manifest hash and rights flags in `markPromoOutcome`.
- `claimPromo` / `markPromoOutcome` run through `runLedgerCommand` (wallet row `FOR UPDATE` first per D10, idempotent by key, terminal business rejections persisted). `claim_unknown` means no second claim is ever offered.

**Guard design: content, not depth.** S4 adds no SECURITY DEFINER function (privilege model B keeps exactly one: S2's apply function). The claim-state UPDATE guard therefore binds by content: an UPDATE of `(state, event_seq)` is accepted only if it equals the next recorded event (`event_seq = OLD.event_seq + 1`, a matching event row exists, edge legal, identity columns immutable). A `pg_trigger_depth() > 1` check is kept as defence in depth only; it is bypassable through a TEMP-table trigger (S2 lesson), which is why it is not the binding check. Honest limit: mutation M2 below (disabling the depth check) is **not** detected by any test, because the content check independently rejects every case the depth check would. This is documented rather than hidden.

## S5 addendum — authorize → reserve → release, bundle packages (migration `0005_reservations`)
Status: **proposed, implemented locally for S5 only; not deployed.** Plan step: `M7-Plan.md` §7 S5. Nothing in S5 adds a flag, a dependency, a route, an `.env` key or a runtime import (`ledger-isolation.test.ts`, D13: `ledger-reservations.ts` is on the ledger-source list and nothing under `apps/` imports it). `0005_reservations.sql` adds no `GRANT`, no role, no `OWNER TO`, inserts no rows, references nothing in `vynvori_identity` and no Medusa object; the only `REVOKE` is function-level `FROM PUBLIC`. It is journal number 0005, applied after S4's `0004_promo_claims` (merged first; the two migrations touch disjoint objects, and each rollback refuses while a later migration is journaled, so the order down is 0005 then 0004). No real credit grant source is registered by any means: the S2 proofs (runtime has no privilege on `ledger_grant_sources`, the table is empty after migration, an entry naming an unregistered source is rejected) are unchanged and still run.

**What S5 adds.** Tables `ledger_authorizations`, `ledger_packages`, `credit_reservations`; the `ledger_entries.reservation_id` FK (`ALTER TABLE … ADD CONSTRAINT ledger_entries_reservation_fk`, dropped first by the rollback); the partial unique index `ledger_entries_one_terminal_per_reservation` (at most one of `release`/`settle`/`hold` per reservation; S2's `UNIQUE(cause_kind, cause_ref)` with `cause_ref = {reservation_id}:{entry_kind}` already gives `UNIQUE(reservation_id, entry_kind)`); nine trigger functions; `packages/db/src/ledger-reservations.ts` (`authorizeQuote`, `releaseReservation`, `recordWorkflowRef`, `getReservation`) and its `./ledger-reservations` export. S2's temporary `ledger_entries_s2_grant_only` constraint is replaced by `ledger_entries_s5_kinds CHECK (entry_kind IN ('grant','reserve','release'))`: `settle` and `hold` stay impossible until S6 widens the set (and the S5 binding trigger refuses them too: two layers, both tested).

**Design (binding for S5).**
- Every S5 operation is a ledger **command of the reservation owner through `runLedgerCommand`**, so it takes the wallet row `FOR UPDATE` first (A4, proven for the three new kinds `reservation_authorize`, `reservation_dispatch`, `reservation_release`, now registered in A4(2)). Lock order: wallet → reservation rows by id (`FOR UPDATE`, user-scoped). No lineage lock. The binding trigger takes the same order itself (wallet `FOR UPDATE`, then the reservation), so a raw-SQL writer cannot deadlock against a library command.
- After the command commits, the result is read back on any `LedgerDb` shape (a pool's own `query`, else one checked-out connection that is always released). A failure of that read is `TRANSIENT`, never a command failure: the command is durable and a retry with the same key replays it. A business rejection is persisted under its key, so recovering from, say, a release attempted before dispatch needs a **new** key.
- `authorizeQuote` (customer actor; `userId` is the authenticated user, never a body field) checks, in this order, inside the command: owner match (`NOT_FOUND`) → not a promo (`INVALID_TRANSITION`; promos are S4 claims) → lineage not already authorized (`QUOTE_STALE`) → S3 `assessQuoteForAuthorization` with the **injected clock** (`now == expiresAt` is expired) and the price policy port (`QUOTE_STALE` | `QUOTE_EXPIRED` | `ALLOCATION_INVALID`) → contract guard (`quoteGrantsEligibleBundleAuthorization` ⇒ else `DOWNSTREAM_USE_UNAVAILABLE`; `finalQuoteHasRequiredConsent` ⇒ else `TERMS_NOT_APPROVED`) → `AuthorizationEligibilityPort.check`, **called inline on every new command and never cached**, its answer parsed with `EligibilityDecisionV1Schema` (a malformed answer is `INVALID_INPUT`, never an approval; a denial persists its own code, including `CANCELLATION_WINDOW_UNDISCLOSED`) → explicit consent to exactly the quote's consent text version (`TERMS_NOT_APPROVED`) → final only: the caller's own original package (`NOT_FOUND`) → available units ≥ the quote's maximum hold (`INSUFFICIENT_CREDITS`). An absent port is `INVALID_INPUT` **before any SQL** (D7: absent ⇒ deny; the repository ships no implementation, so nothing can authorize in production in W1). Then, atomically: one authorization, the bundle's package (born `authorized`), and per frozen allocation one reservation (born `authorization_requested`, ledger-generated `operation_id`) plus one `reserve` entry whose evidence is the authorization itself. Business rejections persist under the key (S2 savepoint), so a top-up never turns an old press into an authorization; a new press needs a new key. The ledger never computes a split: it reserves exactly the allocation vector S3 froze.
- `releaseReservation` (system actor, `expectedUserId`): evidence must parse as `TransitionEvidenceV1` with `transition: "release"` / `evidenceKind: "verified_zero_charge_failure"` **before any SQL** (anything else, including an unknown outcome, is `EVIDENCE_INVALID`); inside the command its `operationId` must equal the reservation's own operation, read from the database (`EVIDENCE_INVALID`, persisted), and the reservation must be `reserved` **and dispatched** (`workflow_ref` recorded) — a never-dispatched reservation stays reserved for a human (S8 orphan finder; founder question Q9). The full hold returns in one entry, never netted against a sibling. The evidence reference is stored on the entry.
- `recordWorkflowRef` (system actor): records the dispatch marker once (`NULL → value`) on a `reserved` reservation; the same value again is a no-op; any other change is `INVALID_TRANSITION`. It moves no units and changes no state.
- `ledger_packages` are immutable in S5 (no transition exists until S7). A final reservation records `original_package_id` and `pre_attempt_package_state` (`CHECK`-required for finals, forbidden for bundles; C-02).
- Renewing an authorized lineage is refused by a `BEFORE INSERT` trigger on `ledger_quotes` (23000), which S3's `renewQuote` already maps to `QUOTE_STALE`; `ledger-quotes.ts` is unchanged.

**Privilege model B for reservations (hard gate satisfied).** Reservation state is written **only** by `ledger_entries_apply_to_reservation()`, the second and last `SECURITY DEFINER` function in the migration set, fired `AFTER INSERT` on `ledger_entries`; its own `UPDATE` re-checks user, source state and units. `credit_reservations_update_guard()` rejects every state change unless `pg_trigger_depth() > 1` **and** `current_user` equals the owner of that function, compared by name (`pg_get_userbyid`, never a `regrole` cast), and allows only the S5 edges `authorization_requested → reserved` and `reserved → released`; identity and unit columns are immutable for everyone. Every one of the nine trigger functions pins `TG_RELID`/`TG_OP`/`TG_WHEN`/`TG_LEVEL`, sets `search_path = pg_catalog, pg_temp`, and is `REVOKE ALL … FROM PUBLIC`. The binding trigger (`ledger_entries_bind_reservation`, invoker-rights, `BEFORE INSERT`) requires an applied command of the matching kind **written in the current transaction** (the command row's `xmin`, widened to `xid8` against `pg_current_xact_id()`, must be `pg_xact_status = 'in progress'`; an old, frozen or truncated xid fails closed, except under the wraparound collision in honest limit 5), locks the reservation, and checks state, units and evidence. Authorizations, packages and reservations are likewise insert-only within their own command's transaction; deferred constraint triggers fail the commit if a reservation is left `authorization_requested` or an authorization does not reserve every allocation (one package for a bundle, none for a final).

**S9 grants this design needs (founder-executed; never in a migration).**
- Runtime role: `SELECT, INSERT` on `ledger_authorizations`, `ledger_packages`, `credit_reservations`; `UPDATE (workflow_ref)` on `credit_reservations` (also what its `FOR UPDATE` row locks need). `SELECT` on `ledger_authorizations` is needed even by `issueQuote`/`renewQuote` once 0005 is applied (the lineage-authorized trigger reads it). No `UPDATE` of `state` or units, no `DELETE`/`TRUNCATE`, no `EXECUTE` on any ledger function.
- Reservation definer owner: a dedicated `NOLOGIN NOSUPERUSER NOBYPASSRLS NOCREATEROLE` role holding **exactly** `USAGE` on `vynvori_ledger`, `SELECT` and `UPDATE (state)` on `credit_reservations`; `ALTER FUNCTION vynvori_ledger.ledger_entries_apply_to_reservation() OWNER TO` it. `ledger-privileges.test.ts` proves the path works with exactly these and fails when any one is removed. It may be the same role as the wallet definer owner or a separate one (founder decision with the S9 grants proposal).

**Honest limits (stated, not overclaimed).**
1. The runtime role keeps `INSERT` on `ledger_commands`, `ledger_entries` and the three S5 tables, and `UPDATE (workflow_ref)`, by design (it runs the library). The database therefore enforces the **shape** of every S5 write, not the business decisions behind it. Code holding the runtime role's privileges, writing raw SQL instead of calling the library, could:
   - write an authorization for **any** user's latest, unauthorized, non-promo quote without real consent or an eligibility check (consent, the eligibility port and the funds check run in TypeScript; the wallet `>= 0` `CHECK` is the only database funds backstop, and `Σ hold_units` against the quote's maximum hold is likewise checked in TypeScript only). The effect is that user's own credits reserved against their own quote: nothing is minted or moved to anyone else, but the credits stay locked until a human or the S8 orphan finder acts;
   - set `workflow_ref` on any reserved reservation, which is all the "dispatched" gate checks;
   - then write a `reservation_release` command and a `release` entry with any evidence reference: evidence is caller-asserted (contract note on `TransitionEvidenceV1Schema`), and S5 records it, binds it to the reservation's own operation in TypeScript, and checks its shape in the database.

   None of this mints credits, moves units across users or wallets, or releases twice, and reservation state still moves only through entries (the hard gate). It is the same trust boundary as S2's grant path. It matters more from S6 on, when a forgeable zero-charge release would sit next to a real settle path. The fix is a `SECURITY DEFINER` command path for `reservation_authorize`, `reservation_dispatch` and `reservation_release` with its own owner (or at least restricting who can set `workflow_ref`), which is the same architecture question as the grant-source hard gate (M4/W3). **Founder question**, raised in the S5 PR; S5 does not decide it.
2. Two raw connections that bypass the wallet lock could race a renewal against an authorization of the old version; `UNIQUE(quote_id)` on authorizations still allows at most one authorization per lineage, and the renew trigger refuses a renewal once one exists. Through the library the race serializes on the wallet lock (tested 50 + 50).
3. A schema-valid `QuoteViewV3` cannot express an ineligible bundle, so the contract guard in `authorizeQuote` is reachable only through a tampered stored view, which `assessQuoteForAuthorization`'s hash check already rejects; it stays as defence in depth. Ineligibility in practice arrives through the eligibility port (tested for every denial code); that such views cannot be issued is tested too.
4. `releaseReservation` does not verify the Plane B evidence reference against a provider record (the `ProviderOutcomeEvidencePort` has no implementation in W1).
5. The "command written in this transaction" check compares the command row's raw 32-bit `xmin`, widened against `pg_current_xact_id()`. Frozen rows keep their raw `xmin`, and a future xid makes `pg_xact_status` raise, so both fail closed. The one theoretical gap is a wraparound collision: an old command whose raw `xmin` equals the low 32 bits of a different, currently running transaction. That needs more than 2^32 transactions to pass, and its effect is bounded because reserve and release causes are unique per reservation.
6. `AuthorizationEligibilityPort.check` runs inside the command, while that user's wallet row is locked. A slow rights check therefore blocks only that user's own ledger commands; past the 30-second idle-in-transaction timeout the connection is killed and the caller gets `LEDGER_OUTCOME_UNKNOWN` (a replay with the same key then converges). Port implementations must answer well inside that limit.
7. A final reservation may name any of the caller's own packages as its original package, including one whose bundle reservations were all released. Package eligibility for a final is an S7 rule.

**What S6 adds.**
- `0006` drops S5's temporary `ledger_entries_s5_kinds` constraint. It then `CREATE OR REPLACE`s exactly three S5 functions, each a strict superset of its 0005 body. A static test checks that every 0005 refusal message survives.
  - `ledger_entries_bind_reservation()` (invoker, `BEFORE INSERT`) now admits `settle` and `hold`. It lists the admitted kinds itself (`grant`, `reserve`, `release`, `settle`, `hold`), which is why the kind constraint can go. S2's `ledger_entries_kind` and `ledger_entries_sign_shape` still bound the shape.
  - `ledger_entries_apply_to_reservation()` (**`SECURITY DEFINER`**, restated; `CREATE OR REPLACE` keeps its owner and ACL) gains two `UPDATE` branches. Each re-checks state `reserved`, the dispatch marker and the units.
  - `credit_reservations_update_guard()` keeps the same depth **and** function-owner test. It allows exactly `authorization_requested → reserved` and `reserved → released | settled | reconciliation_hold`. There is no edge out of `settled` or `reconciliation_hold`. This is tested directly: the function owner, at depth 2 through a TEMP trigger, is refused every such edge, while the control edge works.

- No new definer: the migration set keeps exactly two.

**Design (binding for S6).**
- **Settle.** `settleReservation` uses a system actor with `expectedUserId` (D11), parsed by `LedgerInternalCommandV1Schema`. It settles only on evidence that meets all of these:
  - parses as `TransitionEvidenceV1` with `transition: "settle"` before any SQL;
  - passes `canMarkReceiptSettled` (never `outcome_unknown` or a vendor-charge message) and `canMarkOperationDelivered` (verified manifest hash and owner/rights);
  - has an `operationId` equal to the reservation's own operation, read from the database inside the command;
  - targets a reservation that is `reserved` and dispatched.

  One `settle` entry consumes exactly the frozen `charge_units` and returns `hold_units − charge_units` to `available`. The amount is never taken from the caller, so a settle cannot exceed the hold. The binding trigger refuses any other split (`delta_reserved = −hold`, `delta_consumed = charge`, `delta_available = hold − charge`), and so does the definer's own `UPDATE`.
- **Hold.** `holdReservation` takes `outcome_unknown` or `persistence_failed_under_review` evidence with the matching reason, under the same binding and dispatch rules. It moves the **full** hold of exactly this reservation to `held_for_review` (state `reconciliation_hold`). No customer debit is inferred, nothing is retried and nothing is released. Siblings are untouched and settle or release independently (tested). Nothing in W1 leaves the hold: the guard has no edge out, no exported function names it, and remedy is a later milestone (D2).
- **Persisted rejections and lock order.**
  - An operation mismatch (`EVIDENCE_INVALID`) or a wrong state (`INVALID_TRANSITION`) is persisted under the idempotency key, as in S5.
  - A second settle, or a settle or hold of a released, settled or held reservation, is `INVALID_TRANSITION`, with balances unchanged.
  - Lock order is wallet → reservation (A4(1), proven for both new kinds).
- **Out of order: neither case is persisted, so retrying with the same key works once the missing row commits (tested).**
  - Evidence for a reservation that does not exist yet, or that belongs to another user, is `NOT_FOUND`.
  - Evidence that arrives before the dispatch marker is `INVALID_TRANSITION` thrown as a plain `LedgerError`. This differs from S5's release, on purpose. A component that learns of an unknown outcome before its dispatch marker commits must still be able to hold under its original key. Review LOW-1.
- **Vendor-cost evidence.**
  - `recordVendorCostEvidence` writes only `vendor_cost_evidence`, in one autocommitted statement. It takes no wallet lock, opens no ledger command and names no other ledger table (static test).
  - The table has no FK in either direction. Its only triggers are `reject_mutation()`, covering append-only and no `TRUNCATE`. No ledger function body mentions it (catalog test).
  - `reservation_id` is an optional reconciliation hint and is deliberately not checked.
  - Recording is idempotent on `(operation_id, evidence_kind, evidence_ref)`. A changed amount or hint under the same key is `IDEMPOTENCY_CONFLICT`. `recorded_by` is provenance, not content.
  - Usage, invoice and unknown evidence for reserved, held and settled operations change **zero rows** in `wallets`, `ledger_entries`, `credit_reservations`, `ledger_commands` and `ledger_authorizations` (md5 fingerprint test).
- **Micro-USD mapping.**
  - `amount_usd_micros` is an exact integer number of millionths of a US dollar, from 0 to 2^53 − 1. It is `NULL` when the vendor reported no amount, and must be `NULL` for `unknown`.
  - `internal.ts`'s `privateVendorCostUsd: number` maps as `amountUsdMicros / 1e6`, for internal display only.
  - The ledger never converts a float into micros (no rounding rule is approved) and never converts USD into credits (no rate card exists).
  - Vendor cost never reaches a customer projection: `FORBIDDEN_PUBLIC_FIELDS` already lists `privateVendorCostUsd` and `vendorCostEvidence`.

Preferably grant it to a dedicated internal reconciliation role rather than the customer-path runtime role. The table is append-only and unattributed, so whoever holds `INSERT` can add rows that only a superuser can remove (review LOW-2).

## S7 addendum — refinement slots, package transitions and closure (migration `0007_refinement_slots`)
Status: **proposed, implemented locally for S7 only; not deployed.** Plan step: `M7-Plan.md` §7 S7 (with D9, F11/Q7, §2, §3). Nothing in S7 adds a flag, a dependency, a route, an `.env` key or a runtime import (`ledger-isolation.test.ts`, D13: `ledger-entitlements.ts` is on the ledger-source list and nothing under `apps/` imports it). `0007_refinement_slots.sql` adds no `GRANT`, no role, no `OWNER TO`, inserts no rows, references no Medusa object, registers no credit grant source and writes no ledger entry (refinements never touch a wallet bucket). It replaces exactly one S5 object (the `ledger_packages_immutable` trigger, which rejected every update "until S7") and does not replace or alter any 0005/0006 function. The package edge guard in root (`canTransitionPlaneCBundle`) and the operation guards are imported, not edited.

**What S7 adds.** Tables `ledger_package_events`, `refinement_slots`, `refinement_slot_events`; two pure edge functions; nine trigger functions (two of them `SECURITY DEFINER`); `packages/db/src/ledger-entitlements.ts` (eleven commands and reads, export `@vynvori/db/ledger-entitlements`). The migration is additive with a tested up/down/up; the down script refuses while any row exists in the three new tables, while any package has left `authorized`, or while a later migration is journaled.

**Design (binding for S7).**
- Every S7 operation is a ledger **command of the package owner through `runLedgerCommand`** (ten new command kinds, registered in A4(2): `refinement_skip`, `refinement_restore`, `refinement_pending`, `refinement_unknown`, `refinement_consume`, `bundle_record_delivery`, `bundle_open_refinements`, `bundle_begin_closure`, `bundle_close`, `bundle_reopen`). Lock order: wallet → package `FOR UPDATE` → slots by ordinal → reservations. Business refusals (`INVALID_TRANSITION`, `EVIDENCE_INVALID`, `TERMS_NOT_APPROVED`) are persisted per idempotency key.
- **Package state changes only through `ledger_package_events`** (insert-only). A `BEFORE INSERT` binding trigger (invoker rights) demands an *applied command of the right kind written in this transaction* (xid8 widening plus `pg_xact_status = 'in progress'`), the stored `from_state`, an allowed edge, and the per-edge evidence. An `AFTER INSERT` `SECURITY DEFINER` function (`ledger_package_events_apply`) is the only writer of `ledger_packages.state` and the only inserter of `refinement_slots` (it creates the two slots when the package first becomes `open_for_refinements`). A deferred constraint trigger makes each event atomic with its consequences (two slots on opening; every slot resolved on closing; forfeiture only together with the closing event).
- **Slot state changes only through `refinement_slot_events`**, same pattern (`refinement_slot_events_apply`).
- **Edges.** Packages: `authorized → partial | delivered_3_of_3`, `partial → delivered_3_of_3`, `delivered_3_of_3 → open_for_refinements`, `open_for_refinements → closure_pending`, `closure_pending → closed`, and the guarded C-02 reopen `closure_pending → open_for_refinements`. Slots: `available ↔ skipped`, `available → pending`, `pending → unknown | used`, `unknown → used`, `available | skipped → forfeited`. A test compares the database edge function with root's guard for all 64 package pairs; the only differences are the declared ones (reopen is db-only and guarded; `quoted → authorized`, `closure_pending → remedy_pending` and `remedy_pending → closed` are root-only and deferred).
- **Delivery.** `bundle_record_delivery` takes an artifact count and an evidence reference; only exactly 3 durable artifacts reach `delivered_3_of_3`, 0–2 reach `partial`. A bundle opens once, from `delivered_3_of_3` only. Internal names are used in the database (`open_for_refinements`); the customer name (`refinements_open`) is mapped by `toCustomerPackageState` at the projection boundary.
- **Closure.** `closure_pending` blocks restore, skip, pending and consume. Beginning closure is refused while a refinement is `pending` or `unknown`. Closing forfeits only `available`/`skipped` slots, in the same transaction as the closing event, under the **disclosed notice**: the notice version must equal the one stored with the disclosing quote (`TERMS_NOT_APPROVED` otherwise). A quote that discloses no notice can never close a package (the feature stays closed). A `used` slot stays `used`. Closing is refused while any final of the package is unresolved (`authorization_requested`, `reserved`, `reconciliation_hold`, `operator_remedy`). Causes are `final_delivered` (a settled final) and `explicit_close`; `explicit_close` is refused once a final settled.
- **No clock, no expiry.** There is no clock-based expiry anywhere (a static test scans the module and the migration); `approved_expiry` is not an allowed cause because no approved terms exist, and that value is rejected as `INVALID_INPUT`.
- **C-02 reopen.** `reopenBundleAfterUnchargedFinal` reopens a package only for a **released first final** that began on an open package, whose committed `release` entry carries `verified_zero_charge_failure`, when closure began *because of this final* (the latest `closure_pending` event is `final_authorized` for it) and no sibling final is settled or unresolved. Slots come back exactly as they were; none is recreated. A later revision on a closed package never reopens or recreates slots. This is stricter than the plan's wording (an explicit close request is never undone by a final, and every other final must be released).
- **Ownership and identity.** Every command and read is scoped by the authenticated `userId` (the verified issuer + subject mapping lives upstream); another user's package or slot is `NOT_FOUND` and nothing is recorded. Operation ids are unique system-wide, a delivered version consumes at most one slot of a package, and a source version binds once.
- **Free text.** `evidenceRef` (1–512) and `closureNoticeVersion` (1–256) are printable ASCII only, enforced in TypeScript and by `CHECK` constraints on all affected tables. A driver error while reading state is surfaced as `LedgerError("TRANSIENT")`, never as a raw driver message.

**Privilege model B for packages and slots (hard gate satisfied).** `ledger_packages_update_guard()`, `refinement_slots_insert_guard()` and `refinement_slots_update_guard()` reject every write unless `pg_trigger_depth() > 1` **and** `current_user` is the owner of the corresponding apply function (compared by name, never a `regrole` cast); depth alone is never enough. Every S7 function pins `search_path = pg_catalog, pg_temp`, schema-qualifies every object, uses no dynamic SQL, is `REVOKE ALL … FROM PUBLIC` (the two pure edge functions excepted) and the two definers verify what fired them (`TG_RELID`, `TG_OP`, `TG_WHEN`, `TG_LEVEL`).

**S9 grants this design needs (founder-executed; never in a migration).**
- Runtime role: `SELECT, INSERT` on `ledger_package_events` and `refinement_slot_events`; `SELECT` on `refinement_slots`; `SELECT` on `ledger_packages` (already granted); lock-only `UPDATE (package_id)` on `ledger_packages` and `UPDATE (slot_id)` on `refinement_slots` (identity columns the guards never let change; `SELECT … FOR UPDATE` needs an `UPDATE` column privilege, exactly as `UPDATE (user_id)` on wallets does). **Honest limits (stated, not overclaimed).**
1. The runtime role keeps `INSERT` on the two event tables and the command table by design (it runs the library). The database enforces the **shape and graph** of every S7 write, not the business decisions behind it. Code holding the runtime role's privileges and writing raw SQL could, for a user whose package state allows the edge, record an event with caller-asserted evidence: a delivery count, an `explicit_close_request` (customer consent is not recorded in a ledger-verifiable form), or slot evidence. It still cannot mint credits, move units, touch a wallet bucket, skip an edge, forfeit without the closing event, change state outside an event, or leave a slot unresolved on a closed package. 2. Evidence verification is the caller's: whether a delivery really produced three durable artifacts, or a slot's operation really produced the delivered version, is a Plane B / M6b integration seam. S7 binds evidence to the slot's own operation and stores it; it does not call a provider.

4. There is no `pending → available` edge for a refinement that failed uncharged, and `unknown → used` is allowed (reconciliation evidence). Both are declared design choices pending founder confirmation.
5. A system actor learns whether an operation id is already used (ids share a namespace with reservations' operation ids). System actors are trusted components, not customers.
6. Rate limiting belongs at the API layer (there is no API in S7).
7. `LedgerError` exposes `sqlstate`/`constraint` fields (ledger-core, outside this lane) which carry internal names; the S7 library only ever raises codes.
8. The runtime's `FOR UPDATE` lock grants let raw SQL lock any user's package or slot rows; two raw sessions could deadlock (the library locks in the documented order).
9. 0006 (S6) is on `main` and 0007 follows it in `plan.json`; the migrations test runs `down7` before `down6`. S7 replaces none of the three S5 functions S6 replaced. ## S8 addendum — read-only wallet-invariant check and orphaned-reservation finder (no migration)
Status: **proposed, implemented locally for S8 only; not deployed.** Plan step: `M7-Plan.md` §7 S8 (D14, plus the S2 follow-up "S8"). S8 adds **no migration, no table, no trigger, no role, no flag, no dependency, no route and no runtime import** (`ledger-isolation.test.ts`: the module is write-free by a static test and absent from every app). Export `@vynvori/db/ledger-invariants` has exactly two functions.

**What S8 adds.** `packages/db/src/ledger-invariants.ts`: `checkWalletInvariants(db)` and `findOrphanedReservations(db, { olderThan })`. Both accept a `LedgerDb` (a pool or an `acquire()` provider, never a bare client), open **one `READ ONLY`, `REPEATABLE READ` transaction**, send only `SELECT`/`WITH` statements (timeouts are set with `set_config(..., true)` so even those are `SELECT`s), take no row lock (only the `ACCESS SHARE` table locks every `SELECT` takes, so do not run the checker during a migration) and run no ledger command, and always `ROLLBACK`. After `BEGIN` the checker verifies `transaction_read_only = on` and `transaction_isolation = repeatable read` and aborts otherwise (a pooler or dirty connection can ignore the options), and pins `search_path = pg_catalog, pg_temp` for the transaction. One snapshot means a concurrent command can never produce a false finding. A driver failure surfaces only a `LedgerError` code and SQLSTATE; a connection with no server report is destroyed, never reused.

**Invariants (D14 plus the checks the plan and review added).** Each finding carries `invariant`, `userId`, `subjectId` and string/boolean `detail` (balances are text, never rounded; capped at 100 per invariant with a `truncated` list).
- `WALLET_BUCKET_MISMATCH`: each wallet bucket equals the sum of its entry deltas, and `revision` equals the entry count (the apply function adds 1 per entry). `ENTRY_UNBALANCED`: every entry's five deltas sum to zero (re-derived in `numeric`, so a dropped `CHECK` is still caught). `WALLET_BUCKET_OUT_OF_RANGE`: any bucket below 0 or above 2^53−1.
- `RESERVED_BUCKET_MISMATCH` (Σ `hold_units` of `reserved`), `HELD_BUCKET_MISMATCH` (Σ `hold_units` of `reconciliation_hold`) and, beyond D14's list, `CONSUMED_BUCKET_MISMATCH` (Σ `charge_units` of `settled`; only settle moves `consumed`).
- `RESERVATION_TRAIL_MISMATCH`: the state follows from the entry trail (none → `authorization_requested`; reserve → `reserved`; reserve + release | settle | hold → that terminal state; anything else, including `operator_remedy`, has no expected state), every entry's amounts equal the reservation's frozen units, and a **committed** `authorization_requested` is itself a finding (0005 defers a check that forbids it).
- `ALLOCATION_SUM_MISMATCH` (per quote version: contiguous indexes, Σ hold = `max_charge_units`, Σ charge = `credits_quoted`; promo quotes have none) and `AUTHORIZATION_ALLOCATION_MISMATCH` (an authorization reserves exactly its quote's allocations, unit for unit, and has the right package count). The second one is the check ADR D5 and the S5 limit say TypeScript alone performs for `Σ hold_units` against the maximum hold; it now has an independent database-side comparison.
- `PROMO_UNIQUENESS_VIOLATED` (more than one claim per issuer + subject, per user, or per operation, re-derived without trusting the unique constraints) and `PROMO_CLAIM_TRAIL_MISMATCH` (state and `event_seq` against the event trail).
- `SYNTHETIC_GRANT_SOURCE_REGISTERED` (D12): each registered `synthetic_test` source, with its grant count and units. Any database with a funded wallet from a test fixture reports it; `ok` is `false` whenever there is any finding.
- **Trigger presence and shape (ADR S2 follow-up).** The module holds a manifest of the 61 triggers migrations 0002–0007 leave on `vynvori_ledger` tables. It reports `TRIGGER_MISSING` (for example after `DROP OWNED BY <definer> CASCADE`), `TRIGGER_DISABLED` (anything but enabled `O`/`A`: a disabled or replica-only trigger leaves the ledger unguarded), `TRIGGER_MISMATCH` (wrong function, timing, level, events, a `WHEN` clause, an `UPDATE OF` column list, arguments, or a constraint trigger that is not deferrable and initially deferred), `TRIGGER_UNEXPECTED` (a trigger on a ledger table that no migration created) and `RULE_UNEXPECTED` (a rewrite rule). It also reports `FUNCTION_PRIVILEGE_MISMATCH` (exactly `ledger_entries_apply_to_wallet`, `ledger_entries_apply_to_reservation`, `ledger_package_events_apply` and `refinement_slot_events_apply` are `SECURITY DEFINER`, no other function) `FUNCTION_SEARCH_PATH_UNPINNED` (every function keeps `search_path = pg_catalog, pg_temp`), and `FUNCTION_BODY_CHANGED` / `FUNCTION_UNEXPECTED` (an `md5(prosrc)` fingerprint of each of the 32 functions; a replaced `reject_mutation()` that returns `NEW` is caught).
- **Guards that are not triggers (review MEDIUM-2/LOW-1/LOW-2).** `UNIQUE_KEY_VIOLATED` re-derives (counts only; no key value is selected) the double-effect and idempotency guards: `ledger_entries(cause_kind, cause_ref)`, `ledger_commands(scope, idempotency_key)`, one authorization per quote and quote version, one reservation per allocation and operation, one terminal entry per reservation. `ENTRY_ORPHANED` finds entries with no wallet, a grant with no registered source, or a reservation entry with no (or a foreign) reservation. `CONSTRAINT_NOT_VALIDATED` and `INDEX_INVALID` find a constraint or index that exists but does not cover every row. `ROW_SECURITY_ENABLED` reports row-level security or any policy on a ledger table. `SESSION_SETTING_OVERRIDE` reports a role or database setting of `session_replication_role` or `row_security`.

**Orphans (D14, D6).** `olderThan` is a required `Date` with no default (type-level `@ts-expect-error` cases, plus a runtime `INVALID_INPUT` before any SQL for a missing, non-`Date` or invalid value). Classes: `reserved_never_dispatched` (`reserved`, no `workflow_ref`), `reserved_dispatch_stale` (`reserved` with a `workflow_ref` and no terminal entry) and `hold_present` (`reconciliation_hold`). Report-only: nothing is released, settled, held, dispatched or resolved (Q9 stays open: a never-dispatched reservation stays `reserved` for a human). The report names reservation, user and operation ids and units; it never reads or returns a workflow reference, evidence, idempotency key or vendor cost (static tests).

**Maintenance rule (binding for later migrations).** A migration that adds, renames or drops a trigger on a ledger table, or adds a `SECURITY DEFINER` function, must update the manifest in `ledger-invariants.ts` in the same PR. The clean-state test fails otherwise (`TRIGGER_UNEXPECTED` / `TRIGGER_MISSING`); that is the intended review prompt, not a flake.

**S9 grants this design needs (founder-executed; never in a migration).** A checker role (not the runtime role, which should not need to read the whole ledger) with `USAGE` on `vynvori_ledger` and `SELECT` on `wallets`, `ledger_entries`, `credit_reservations`, `ledger_quotes`, `ledger_quote_allocations`, `ledger_authorizations`, `ledger_packages`, `ledger_grant_sources`, `promo_claims` and `promo_claim_events`; catalog reads (`pg_trigger`, `pg_proc`, `pg_rules`, `pg_class`, `pg_namespace`) are public. **No** `vendor_cost_evidence`, no write privilege of any kind, no trigger or `session_replication_role` right. Running the checker (a schedule, an operator command, a CI step) is deliberately **not** wired in W1: nothing calls it, so an operator or a later step decides when and where it runs.

**Honest limits.**
1. It detects; it does not prove. It compares independent derivations of the same facts, so a corruption that changes both sides consistently (for example a forged balanced grant against a registered source) is not an "invariant" violation. Preventing that is the grant-source and definer-only-command-path hard gates, not this check.
2. It does not inspect role grants, role membership, function owners or `pg_hba`. The rollout re-own procedure and the S9 privilege tests own those. It does not compare every `CHECK` expression and foreign key by name (only that none is unvalidated, plus the re-derived invariants above); a `CHECK` dropped together with a consistent forgery is the same class as limit 1.
3. `reserved_dispatch_stale` and `reserved_never_dispatched` age from the reservation's creation: no dispatch timestamp is stored (`reservation_dispatch` commands carry only a payload hash). A reservation dispatched an hour ago but reserved a week ago is older than a one-day cut-off. A `hold_present` age is the hold entry's.
4. The trigger manifest and the function-body fingerprints are hand-maintained copies of the migrations. The clean-state test proves they equal the migrated database today; they cannot know about a future migration (maintenance rule above, extended to any `CREATE OR REPLACE FUNCTION`). Fingerprints detect a changed body, not whether the new body is harmful.
5. Only the snapshot is consistent: a finding can be repaired a moment later, and a finding can appear the moment after. Reports are for a human, never an automatic repair or release input.
6. A report is internal (user and reservation ids). It must never be mapped into a customer projection.
7. `checkedAt` is the snapshot's database transaction time; the orphan report echoes the cut-off it was given.
8. `findOrphanedReservations` returns units as numbers through `parseSafeUnits`; a reservation corrupted above 2^53−1 makes the orphan report fail with `INVALID_INPUT` (fail closed), while `checkWalletInvariants` reports the same corruption as text. On a very large ledger the whole-table aggregates could exceed the 30 s statement timeout and the check would then always return `TRANSIENT` (fail closed, visible).
9. A report names `operationId` (a caller-allocated business id) as well as user ids; any log shipper or alert must treat both as internal.

**Files outside the S8 row.** (a) `packages/db/tests/ledger-fixture.ts`: one name appended to `LEDGER_TEST_NAMES` (the fixture's own comment says later steps append their file). (b) `packages/db/tests/ledger-isolation.test.ts`: the new module is added to the allowed-source set, the numeric-constant scan and an exact-API test; a static write-free test is added (case-insensitive over every SQL statement, with string literals stripped); and four static checks are narrowed to exempt **only** `ledger-invariants.ts`: the S6 checks that forbid naming `reconciliation_hold`, `'settle',` and `'hold',`, the `vendor_cost` check (the module names the table once, in its trigger manifest), the check that forbids the `session_replication_role` text (the module has one detection pattern for a role or database override), and the write-free scan's allowance for the one `GROUP BY scope, idempotency_key` duplicate count. The write-free test and the `READ ONLY` transaction are the compensating controls. No assertion was removed or loosened for any other file. (c) This addendum. All three follow the precedent of S5–S7; flagged for the founder.
